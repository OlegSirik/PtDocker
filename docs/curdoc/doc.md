# 1. Назначение и границы платформы

Платформа предназначена для автоматизации страхового бизнеса: управления страховыми продуктами, расчёта стоимости, подготовки и выпуска страховых договоров, хранения документов, работы с платежами и поддержки дополнительных страховых процессов.
В текущем техническом контексте платформа строится как единое backend-приложение с модульным разделением ответственности. Это позволяет сохранять единый транзакционный контур и одновременно разделять домены на уровне Java-модулей.

## Что является центральным объектом

Центральным бизнес-объектом выступает страховой контракт/полис. Он связывает продукт, застрахованный объект, участников договора, покрытия, тарифные параметры, документы и финансовые данные.

## Граница ответственности

- Продукт определяет, что и на каких условиях страхуется.

- Calculator вычисляет стоимость на основе тарифных данных и формул.

- Rules применяет бизнес-правила и проверки.

- Policy фиксирует результат оформления как исторический snapshot.

- Files отвечает за документы и объектное хранилище.

- Payments содержит финансовый контур; точный provider lifecycle требует дальнейшей фиксации.

# 2. Архитектурный стиль

Текущая архитектура определяется как modular monolith: один backend runtime, внутри которого существуют отдельные Gradle-модули с собственными зонами ответственности.

```text
Client / Browser / Partner
          |
          v
      HTTP API
          |
          v
+-----------------------------------------------+
|                 Backend                       |
|                                               |
| api | auth | product | calculator | rules    |
| process | numbers | files | payments | db    |
+-----------------------+-----------------------+
                        |
                        v
                   PostgreSQL

```


## Почему модульный монолит

- Единая транзакционная модель для критических страховых операций.

- Меньше инфраструктурной сложности, чем у набора микросервисов.

- Явные границы доменов можно сохранить внутри кода.

- При необходимости отдельный модуль впоследствии может стать самостоятельным сервисом.

Микросервисная декомпозиция не должна считаться текущим фактом. Она может быть будущей эволюцией, но не является описанием сегодняшнего runtime.

# 5. Frontend и пользовательский интерфейс

Frontend построен на Angular/TypeScript. В текущем контексте используются Angular Router, Angular Material, Formly, RxJS, Chart.js и интеграция с Keycloak.
Маршрутизация содержит tenantId как часть URL-контекста. Это важно: tenant является не только внутренним параметром backend, но и частью пользовательского контекста frontend.

```text
/:tenantId/...
       |
       +-- authGuard
       |
       +-- TenantGuard
       |
       +-- tenant-scoped application UI

```

Таким образом, frontend должен передавать и поддерживать tenant context, а backend обязан независимо проверять принадлежность текущего principal к tenant scope. Нельзя считать URL единственным механизмом изоляции.

# 6. Аутентификация

Аутентификация отвечает на вопрос: кто выполняет запрос? В проекте присутствует Keycloak-конфигурация и JWT-инфраструктура. Точная граница ответственности между Keycloak и приложением должна быть подтверждена текущими security-конфигурациями и deployment setup.

## Концептуальный поток


```text
User / Client
     |
     | credentials / SSO
     v
 Identity Provider (Keycloak)
     |
     | access token
     v
 Frontend
     |
     | Authorization: Bearer <token>
     v
 Backend / Spring Security
     |
     +--> validate token
     +--> resolve Principal
     +--> resolve Account / tenant context

```


## Что не следует смешивать

- Authentication — проверка личности/credentials.

- Authorization — проверка разрешений.

- Tenant isolation — проверка области данных.

- Acting account — контекст, от имени которого выполняется операция.

Даже валидный JWT не должен автоматически давать доступ ко всем данным платформы.

# 7. Авторизация

В текущей модели авторизация строится не только вокруг ролей. Зафиксирована комбинация Account hierarchy, explicit privileges и data scope.

## Privilege

Privilege имеет формат &lt;RESOURCE&gt;:&lt;ACTION&gt;. Примеры концептуально: POLICY:READ, POLICY:CREATE, PRODUCT:UPDATE.

## Account и Acting Account

Account представляет субъект/организационный контекст доступа. Acting Account позволяет явно фиксировать, от имени какого аккаунта выполняется действие, что особенно важно при иерархии организаций, брокеров, агентов и дочерних аккаунтов.

## Модель проверки


```text
Request
  |
  v
Authenticated Principal
  |
  +--> Is authenticated?
  |
  +--> Which Account?
  |
  +--> Which Acting Account?
  |
  +--> Has required Privilege?
  |
  +--> Is resource inside Data Scope?
  |
  v
Allow / Deny

```

Privilege отвечает на вопрос <i>что можно сделать</i>, а data scope — <i>с какими данными можно это сделать</i>.

# 8. Tenant и разделение рабочих сред

В многопользовательской системе недостаточно определить, кто имеет доступ к конкретной операции. Необходимо ещё определить, **в каком рабочем пространстве пользователь работает и с какими данными и настройками он взаимодействует**.

Для этого в платформе используется понятие **Tenant**.

Tenant представляет собой изолированную область данных, настроек и пользователей. При этом Tenant не обязан напрямую соответствовать юридическому лицу. Он может представлять любую группу пользователей, для которой требуется отдельное рабочее пространство.

Это делает Tenant универсальным механизмом разделения системы. В одном случае он разделяет разные организации, в другом — филиалы одной организации, линии бизнеса или рабочие среды. В некоторых случаях разделение может использоваться даже для разграничения данных по уровню безопасности.

Например, в системе могут существовать:

```text
Company
Company-branch-1
Company-branch-2

Company-auto
Company-medical
Company-accident

Company-prod
Company-dev

Company-prod
Company-pages
```

Все эти объекты являются Tenant. Для платформы принцип их изоляции одинаков.

## 8.1. Tenant как рабочее пространство

Tenant определяет, **с какими данными и настройками работает группа пользователей**.

Внутри Tenant находятся пользователи, продукты, версии продуктов, правила, тарифы, договоры, документы и другие данные платформы.

```text
Tenant
 ├── Users
 ├── Products
 ├── Product Versions
 ├── Quotes
 ├── Policies
 ├── Documents
 ├── Settings
 └── Other Data
```

Главным признаком принадлежности данных является `tid`.

В целевой архитектуре `tid` присутствует во всех таблицах, содержащих tenant-owned данные. Это позволяет определить принадлежность записи непосредственно, не восстанавливая её через цепочку связанных объектов.

Таким образом, запрос к данным всегда выполняется в контексте конкретного Tenant:

```text
Request
   ↓
Authentication
   ↓
Tenant Context
   ↓
Authorization
   ↓
tid
   ↓
Repository
   ↓
Tenant Data
```

Tenant становится частью контекста выполнения системы.

## 8.2. Разделение пользователей и рабочих сред

Самое простое применение Tenant — разделение по организациям.

Например, одна платформа обслуживает несколько страховых компаний:

```text
Tenant: Company-A
Tenant: Company-B
Tenant: Company-C
```

У каждого Tenant свои пользователи, продукты, договоры, документы и настройки.

Но организационная принадлежность — только один из возможных критериев.

### Филиалы и подразделения

Внутри одной организации может потребоваться дополнительная изоляция по филиалам:

```text
Company
 ├── Company-Moscow
 ├── Company-SPB
 └── Company-Kazan
```

В этом случае разные группы сотрудников работают в разных Tenant. Данные одного филиала не становятся автоматически доступными другому филиалу.

Такой вариант особенно полезен, когда филиалы должны самостоятельно управлять продуктами, пользователями, настройками или другими данными.

### Линии бизнеса

Другой естественный критерий — направление страхового бизнеса.

Например, в одной организации разные группы сотрудников занимаются:

```text
Company-auto
Company-medical
Company-accident
Company-cargo
```

Сотрудники, работающие с автострахованием, получают своё рабочее пространство, сотрудники медицинского направления — другое, а сотрудники НС — третье.

Это позволяет разделить не только пользователей, но и саму конфигурацию продуктов. В Tenant автострахования могут находиться одни продукты, тарифы и правила, а в Tenant медицинского направления — совершенно другие.

При этом отдельная модель `BusinessLine` не обязательна для самой задачи изоляции. Если бизнесу требуется полноценное самостоятельное пространство, Tenant уже предоставляет такой механизм.

### Разделение по уровню безопасности

Tenant может использоваться и там, где причиной разделения является не организационная структура, а требования к безопасности.

Например, основные страховые продукты и договоры могут находиться в рабочем Tenant:

```text
Company-prod
```

А публичные лендинги и API-коды — в другом:

```text
Company-pages
```

В `Company-pages` могут размещаться продукты или настройки, предназначенные для внешнего взаимодействия: лендинги, публичные страницы, специальные API-коды и связанные с ними данные.

Такое разделение позволяет не смешивать основной рабочий контур с данными, которые по своей природе должны быть доступны более широкому кругу пользователей или внешним каналам.

При этом `Company-pages` не является каким-то специальным типом Tenant. Это обычный Tenant, которому организация назначила другое назначение и соответствующий набор пользователей, прав и данных.

### Разделение рабочих сред

Тем же способом можно организовать разные среды работы с продуктами:

```text
Company
Company-dev
Company-test
```

Здесь `Company-dev` может использоваться для разработки и настройки продуктов, а `Company` — для рабочей деятельности.

Для приложения между ними нет принципиальной разницы. Оба являются Tenant и обладают одинаковой моделью изоляции.

Это означает, что `dev`, `test`, `prod`, `pages`, `auto`, `medical` или название филиала не требуют отдельной архитектурной сущности.

**Tenant задаёт рабочее пространство, а его назначение определяется тем, какие пользователи, данные и настройки в него помещены.**

## 8.3. Tenant и группы пользователей

Таким образом, Tenant следует рассматривать прежде всего как **группу пользователей с общей областью данных и настроек**.

Группа может быть сформирована по разным признакам:

```text
                    Tenant
                       │
        ┌──────────────┼──────────────┐
        │              │              │
   Organization     Business       Security
        │              │              │
     Company        Auto/Medical    Prod/Pages
        │
      Branch
```

Эти признаки не являются взаимоисключающими.

Одна организация может иметь отдельные Tenant для филиалов. Внутри другого набора Tenant можно разделить линии бизнеса. Для некоторых данных одновременно может потребоваться отдельное рабочее пространство с более высоким уровнем изоляции.

Поэтому Tenant не следует трактовать как синоним организации.

**Организация — это бизнес-понятие.**
**Tenant — это техническая область совместной работы и изоляции.**

Одна организация может иметь много Tenant, каждый из которых предназначен для своей группы пользователей и своего набора данных.

## 8.4. Tenant и Account

Tenant определяет рабочее пространство, но внутри него всё равно необходимо управлять правами пользователей.

Для этого используется Account.

Если Tenant отвечает на вопрос:

> В каком пространстве работает пользователь?

то Account отвечает на вопрос:

> Кто именно этот пользователь и какие действия ему разрешены?

Поэтому Account существует внутри контекста Tenant:

```text
Tenant
  └── Account
       ├── Account
       ├── Account
       └── Account
```

Account может отражать организационную структуру, подразделения и другие уровни доступа.

При этом Account не заменяет Tenant. Даже если два пользователя имеют одинаковые права, но находятся в разных Tenant, они работают с разными областями данных.

## 8.5. Физическое хранение

Tenant является логическим понятием и не требует отдельной базы данных.

Несколько Tenant могут находиться в одной PostgreSQL:

```text
PostgreSQL
 ├── Company
 ├── Company-dev
 ├── Company-medical
 ├── Company-auto
 └── Company-pages
```

Изоляция обеспечивается через `tid` и правила доступа к данным.

Это позволяет начинать с общей базы данных и не связывать бизнес-модель с конкретным способом физического размещения.

При необходимости Tenant может стать естественной единицей масштабирования или дополнительной физической изоляции. Например, особо чувствительные Tenant могут быть размещены отдельно от Tenant, предназначенных для внешних страниц и публичных интеграций.

При этом прикладная модель остаётся прежней:

```text
Tenant
  ↓
tid
  ↓
Tenant Data
```

Способ физического хранения становится инфраструктурной деталью.

## 8.6. Архитектурный принцип

Tenant — это универсальный механизм разделения пользователей, данных и настроек.

Он может использоваться для:

* разделения разных организаций;
* разделения филиалов одной организации;
* разделения линий бизнеса;
* разделения рабочих сред `dev`, `test`, `prod`;
* разделения основного рабочего контура и внешних страниц или API;
* дополнительной изоляции данных с различными требованиями безопасности.

При этом сама модель остаётся одинаковой:

```text
                     Tenant
                        │
              ┌─────────┴─────────┐
              │                   │
           Users                Data
              │                   │
              └─────────┬─────────┘
                        │
                       tid
```

Название Tenant и его назначение могут различаться, но технический принцип остаётся одним: **каждый Tenant представляет самостоятельную область совместной работы группы пользователей с собственной областью данных и настроек**.

Это позволяет не создавать отдельную сущность для каждого нового варианта разделения. Если появляется новая группа пользователей, которой требуется самостоятельное пространство данных и настроек, она может получить собственный Tenant.

Именно поэтому Tenant является не просто механизмом multi-tenancy, а базовым способом организации рабочих пространств платформы.

## 8.7. Техническая конфигурация Tenant

Если Tenant является самостоятельным рабочим пространством, возникает следующий вопрос: **что именно можно настроить независимо для каждого Tenant?**

Ответ должен быть шире, чем просто список пользователей и продуктов. Tenant должен иметь собственную техническую конфигурацию, которая определяет, каким образом пользователи подключаются к системе, где хранятся их файлы, какие внешние интерфейсы доступны и какие ограничения применяются к потреблению ресурсов.

Эта конфигурация принадлежит Tenant и не должна требовать изменения глобальной конфигурации приложения.

Управлять такой конфигурацией должен пользователь с административными полномочиями внутри Tenant — **Tenant Admin**.

Условно настройки можно разделить на несколько групп.

### Аутентификация

Tenant может самостоятельно определять способ аутентификации пользователей.

Например:

```text id="a4m7kx"
authentication
├── type
├── parameters
└── policies
```

В зависимости от выбранного типа могут настраиваться соответствующие параметры.

Например:

```text id="q8v3pd"
LOCAL
  └── password policy

OIDC
  ├── issuer
  ├── clientId
  ├── clientSecret
  └── scopes

SAML
  ├── entityId
  ├── metadata
  └── certificate
```

Конкретный набор параметров зависит от поддерживаемого механизма.

При этом секреты, такие как `clientSecret`, не должны возвращаться через обычный API чтения настроек в открытом виде.

Таким образом, Tenant может иметь собственную схему подключения пользователей, не меняя глобальную конфигурацию платформы.

### Хранилище файлов

Аналогичный принцип применяется к файловому хранилищу.

Tenant может иметь собственный тип хранилища и параметры подключения:

```text id="j5n2rx"
fileStorage
├── type
└── parameters
```

Например:

```text id="v6c8mw"
S3
  ├── endpoint
  ├── bucket
  ├── region
  └── credentials

MINIO
  ├── endpoint
  ├── bucket
  └── credentials

LOCAL
  └── path
```

Таким образом, разные Tenant могут использовать разные хранилища, не смешивая свои файлы.

Как и для аутентификации, секретные параметры должны храниться защищённым способом и не возвращаться клиенту в открытом виде.

### LLM и внешние сервисы

Tenant-specific должны быть и настройки внешних сервисов, если они используются бизнес-функциями платформы.

Например, LLM-конфигурация может включать:

```text id="e2w7kc"
llm
├── provider
├── model
├── endpoint
├── timeout
└── apiKey
```

При этом API-ключ является секретом и должен храниться отдельно от обычных параметров конфигурации в защищённом виде.

Этот же принцип может применяться к другим внешним интеграциям:

```text id="n7p4qa"
Tenant
 ├── Authentication
 ├── File Storage
 ├── LLM
 ├── External APIs
 └── Other Integrations
```

Не каждая интеграция обязана поддерживаться каждым Tenant. Возможность использования конкретного сервиса определяется конфигурацией и разрешениями платформы.

### API

Tenant может иметь собственную конфигурацию API-доступа.

Здесь важно разделять два понятия.

Первое — **API платформы**, через который пользователи и внешние системы обращаются к Tenant.

Второе — **внешние API и интеграции**, которые сам Tenant использует для взаимодействия с другими системами.

Для API Tenant могут настраиваться:

```text id="k9r5fz"
api
├── enabled
├── authentication
├── rateLimit
├── allowedOrigins
└── integration settings
```

Например, для публичного Tenant `pages` может быть разрешён ограниченный API-доступ, тогда как для основного рабочего Tenant набор доступных API может быть значительно уже.

API-ключи и другие секреты также относятся к защищённым параметрам Tenant.

### Ограничения ресурсов

Некоторые параметры Tenant задают не функциональность, а допустимое потребление ресурсов.

Например:

```text id="c3x8vn"
limits
├── databaseSize
├── fileStorageSize
├── apiRateLimit
├── requestSize
└── other quotas
```

Здесь важно различать **настройку** и **ограничение платформы**.

Например, максимальный размер базы данных может быть установлен платформой для конкретного Tenant:

```text
database quota = 100 GB
```

Tenant Admin может видеть текущее использование и, возможно, запросить изменение квоты, но не обязательно должен иметь возможность самостоятельно установить произвольное значение.

То же относится к rate limit.

Tenant может иметь собственный лимит:

```text
100 requests / second
```

но фактический диапазон допустимых значений должен контролироваться платформой.

Это позволяет Tenant Admin управлять параметрами в пределах предоставленного ему тарифа или политики платформы.

### Что входит в Tenant Configuration

В результате техническую конфигурацию Tenant можно представить следующим образом:

```text id="h4q8mz"
Tenant Configuration
│
├── Authentication
│   ├── type
│   └── parameters
│
├── File Storage
│   ├── type
│   └── parameters
│
├── External Services
│   ├── LLM
│   └── other integrations
│
├── API
│   ├── access
│   ├── authentication
│   └── rate limits
│
└── Resource Limits
    ├── database quota
    ├── file storage quota
    └── request limits
```

При этом не все настройки являются свободно изменяемыми.

Часть параметров может задаваться только платформой, часть — Tenant Admin, а некоторые значения могут быть доступны для просмотра, но не для изменения.

Поэтому для каждой настройки следует определить не только значение, но и **кто имеет право им управлять**.

### Tenant Admin

Tenant Admin является владельцем административной конфигурации Tenant.

Его зона ответственности может включать:

* пользователей и их доступ;
* способ аутентификации;
* настройки файлового хранилища;
* настройки внешних интеграций;
* LLM;
* API-доступ;
* rate limits в разрешённых пределах;
* просмотр использования ресурсов;
* доступные квоты и другие технические параметры Tenant.

При этом Tenant Admin не должен автоматически получать права администратора всей платформы.

Это принципиальное разделение:

```text id="s6k2wp"
Platform Admin
      │
      ├── manages platform
      ├── defines available capabilities
      └── defines limits
              │
              ↓
         Tenant Admin
              │
              ├── manages Tenant
              ├── configures allowed capabilities
              └── manages Tenant users
```

Платформа определяет, **что вообще разрешено Tenant**, а Tenant Admin определяет, **как разрешённые возможности используются внутри его рабочего пространства**.

Например, платформа может разрешить Tenant использовать S3, MinIO и локальное хранилище. Tenant Admin выбирает S3 и задаёт параметры конкретного хранилища.

Или платформа может установить максимальный rate limit в 1000 запросов в секунду, а Tenant Admin выбрать значение 200 запросов в секунду.

Такой принцип позволяет сохранить управляемость платформы и одновременно сделать Tenant действительно самостоятельным рабочим пространством.

В итоге Tenant становится не только контейнером бизнес-данных, но и **самостоятельным контекстом конфигурации системы**.

```text id="p7m3xd"
Tenant
│
├── Users
├── Business Data
├── Products
├── Documents
│
└── Technical Configuration
    ├── Authentication
    ├── File Storage
    ├── LLM
    ├── API
    ├── Integrations
    └── Resource Limits
```

Именно это позволяет использовать одну платформу для существенно разных сценариев: от обычной рабочей среды страховой компании до отдельного Tenant для разработки, специализированной линии бизнеса или публичных страниц.

# 9. Product Domain

Продукт является конфигурацией страхового предложения. Внутри него находятся версии, покрытия, риски, тарифные таблицы, формулы, правила и документы.

```text
Product Family / Group
          |
          v
       Product
          |
          +---- Product Version
                    |
          +---------+---------+---------+
          |         |         |         |
       Coverages  Risks    Rates      Rules
                                                                     +-- Formulas

```


## Версионирование

Опубликованная Product Version не должна изменяться задним числом. Lifecycle: DRAFT → PUBLISHED → DEPRECATED.
Это необходимо для воспроизводимости расчёта и исторической корректности полиса: старый договор должен ссылаться на ту версию продукта, на которой он был оформлен.

# 10. Pricing, Calculator и Rules


## Calculator

Модуль Calculator использует rate tables, formulas и variables. Общая концепция расчёта:

```text
Input contract data
       |
       v
Risk / Rating factors
       |
       v
Rate Tables + Formulas
       |
       v
Adjustments / Discounts
       |
       v
Premium

```


## Rules

Модуль Rules использует CEL для вычисления бизнес-условий. Это позволяет отделять конфигурируемые eligibility/validation правила от Java-кода.

## Среды

- DEV — настройка и тестирование продукта/правил.

- PROD — использование опубликованной версии.

- Published configuration должна быть воспроизводимой.

Quote и Policy могут использовать один и тот же входной InsuranceContractRequest, если фактические поля совпадают. Разделение Quote и Policy является прежде всего lifecycle/resource distinction, а не обязательным различием входного DTO.

# 11. Quote и Policy lifecycle


```text
InsuranceContractRequest
          |
          +--> POST /quotes
          |       |
          |       +--> calculation
          |       +--> quote
          |
          +--> POST /policies
                  |
                  +--> validation
                  +--> calculation
                  +--> issuance
                  +--> policy snapshot
```

## Quote

Quote — результат предварительного расчёта и предложения. Его задача — показать условия и стоимость до окончательного выпуска.

## Policy

Policy — зафиксированный страховой договор. Для него критична историческая неизменяемость исходных данных: Party и Insured Object сохраняются как snapshot.

## Snapshot semantics

Если Party была создана на основе Master Data через masterPartyId, изменение Master Data после выпуска полиса не должно менять уже существующий полис.

# 12. Страховой контракт

## 12.1. Общая концепция

Страховой контракт — это бизнес-модель, описывающая страхуемую ситуацию, параметры страхования и данные, необходимые для расчёта и оформления договора.

Контракт должен быть независим от конкретного способа передачи данных. Поэтому в платформе разделяются две модели:

1. **каноническая модель данных** — нормализованное бизнес-представление страхового контракта;
2. **транспортная модель** — формат, в котором данные поступают во внутренний API или из внешней системы.

Каноническая модель используется внутри расчётного и бизнес-слоя. Она является основой для:

* расчёта страховой премии;
* применения правил;
* проверки обязательности данных;
* формирования документов;
* работы с договором после его оформления;
* обращения к значениям в формулах.

Транспортная модель предназначена для обмена данными. Она может иметь структуру, удобную для внешнего API, интеграции или конкретного канала продаж.

Общий поток преобразования выглядит следующим образом:

```text
Transport Model
      ↓
Mapping
      ↓
Canonical Model
      ↓
Calculation / Rules / Business Logic
      ↓
Policy / Quote
```

Таким образом, формулы и бизнес-правила не должны зависеть от конкретного JSONPath транспортного протокола.

---

## 12.2. Каноническая модель данных

### 12.2.1. Назначение

Каноническая модель является единым представлением страхового контракта внутри платформы.

Она описывает бизнес-смысл данных, а не способ их передачи.

Например, во внешнем запросе телефон может передаваться как массив:

```json
"phones": [
  {
    "typeCode": "MOBILE",
    "value": "79211112233",
    "isPrimary": true
  }
]
```

В канонической модели это один бизнес-атрибут:

```text
PolicyHolder
└── phone
```

При mapping транспортная модель преобразуется в соответствующее каноническое значение.

Каноническая модель не должна содержать транспортные признаки, которые нужны только для выбора или идентификации передаваемого элемента.

---

### 12.2.2. Правила канонической модели

Для канонической модели применяются следующие правила.

**Первое правило — модель является семантической.**

Каждое поле должно описывать бизнес-значение, а не особенности конкретного протокола.

**Второе правило — каноническая модель не содержит transport metadata.**

В неё не входят:

* `partyId`;
* `masterPartyId`;
* `isPrimary`;
* транспортные `externalId`;
* технические идентификаторы конкретного массива.

**Третье правило — единичные бизнес-значения представлены единичными атрибутами.**

Например:

```text
phone
email
document
address
```

Если транспорт передаёт несколько вариантов, mapping должен определить, какой из них соответствует каноническому значению.

**Четвёртое правило — массив используется только там, где множественность является частью бизнес-модели.**

Например:

```text
drivers[]
transport[]
flightSegments[]
covers[]
risks[]
```

При этом несколько транспортных элементов могут преобразовываться в один канонический элемент.

**Пятое правило — каждый элемент канонической модели имеет уникальный код.**

Код является стабильным идентификатором бизнес-атрибута и используется, в частности, в формулах.

---

### 12.2.3. Уникальные коды элементов

Каждый элемент канонической модели получает уникальный `code`.

Код должен позволять однозначно определить принадлежность атрибута соответствующей бизнес-сущности.

Для верхнеуровневых объектов используются префиксы:

| Префикс | Область        |
| ------- | -------------- |
| `ph_`   | Policy Holder  |
| `pl_`   | Policy         |
| `io_`   | Insured Object |

Например:

```text
ph_person_firstName
ph_person_lastName
ph_person_birthDate
ph_person_age

pl_startDate
pl_endDate
pl_durationYears
pl_durationMonths
pl_durationDays

io_packageCode
io_sumInsured
io_vehicle_vin
```

Код не является JSONPath.

Например:

```text
ph_person_age
```

является каноническим кодом, а:

```text
$.policyHolder.person.age
```

является путём в конкретном представлении данных.

Это позволяет изменять транспортную структуру, не меняя формулы, использующие канонические коды.

---

## 12.3. Структура канонического контракта

Общая структура:

```text
Contract
├── Policy
├── Policy Holder
└── Insured Object
```

На уровне API конкретные объекты могут быть представлены в JSON-структуре, отличающейся от внутренней канонической структуры.

Концептуально контракт состоит из:

```text

│   ├── productCode
│   ├── startDate
│   ├── endDate
│   ├── issueDate
│   ├── currencyCode
│   ├── installmentType
│   ├── durationYears
│   ├── durationMonths
│   └── durationDays
│
├── policyHolder
│   ├── person?
│   ├── organization?
│   ├── document?
│   ├── address?
│   ├── phone?
│   └── email?
│
└── insuredObject
    ├── party?
    ├── person?
    ├── organization?
    ├── document?
    ├── address?
    ├── phone?
    ├── email?
    ├── vehicle?
    ├── vehicleDocument?
    ├── vehicleOwner?
    ├── drivers[]
    ├── cargo?
    ├── carrier?
    ├── transport[]
    ├── delivery?
    ├── vessel?
    ├── consumerElectronics?
    ├── flightSegments[]
    ├── packageCode?
    ├── sumInsured?
    ├── deductibleCode?
    ├── premiumTotal?
    ├── covers[]
    └── *Attributes
```

Не все элементы присутствуют одновременно. Состав `InsuredObject` зависит от страхового продукта.

## 12.4. Policy

`Policy` содержит общие параметры страхового договора.

| Атрибут           | Тип      | Описание                           |
| ----------------- | -------- | ---------------------------------- |
| `productCode`     | string   | Код страхового продукта            |
| `startDate`       | datetime | Дата и время начала страхования    |
| `endDate`         | datetime | Дата и время окончания страхования |
| `issueDate`       | datetime | Дата оформления договора           |
| `currencyCode`    | string   | Код валюты                         |
| `installmentType` | string   | Код схемы рассрочки                |
| `durationYears`   | integer  | Количество полных лет страхования  |
| `durationMonths`  | integer  | Количество месяцев страхования     |
| `durationDays`    | integer  | Количество дней страхования        |

Продолжительность договора представляется отдельными атрибутами `durationYears`, `durationMonths` и `durationDays`.

Эти атрибуты являются частью канонической модели и могут использоваться непосредственно в формулах.

Например:

```text
pl_durationYears
pl_durationMonths
pl_durationDays
```

`installmentType` определяет выбранную схему оплаты согласно конфигурации продукта.

---

## 12.5. Policy Holder

`PolicyHolder` — сторона договора, заключающая договор страхования и являющаяся страхователем.

В зависимости от продукта страхователем может быть физическое или юридическое лицо.

Каноническая модель:

```text
PolicyHolder
├── person?
├── organization?
├── document?
├── address?
├── phone?
└── email?
```

В канонической модели `document`, `address`, `phone` и `email` являются единичными значениями.

Если транспортная модель передаёт несколько документов, адресов или телефонов, mapping должен определить элемент, который будет использован в канонической модели.

---

## 12.6. Person

`Person` содержит данные физического лица.

| Атрибут         | Тип     | Описание                                |
| --------------- | ------- | --------------------------------------- |
| `lastName`      | string  | Фамилия                                 |
| `firstName`     | string  | Имя                                     |
| `middleName`    | string  | Отчество                                |
| `birthDate`     | date    | Дата рождения                           |
| `age`           | integer | Возраст на соответствующую дату расчёта |
| `fullName`      | string  | Полное имя для отображения и печати     |
| `birthPlace`    | string  | Место рождения                          |
| `citizenship`   | string  | Гражданство, ISO 3166-1 alpha-2         |
| `gender`        | string  | Пол                                     |
| `maritalStatus` | string  | Семейное положение                      |
| `inn`           | string  | ИНН физического лица                    |
| `snils`         | string  | СНИЛС                                   |
| `externalId`    | string  | Внешний идентификатор                   |

`age` является свойством `Person` в канонической модели.

Он не выделяется в отдельный `calculationAttributes`, поскольку возраст является бизнес-атрибутом физического лица, который может быть вычислен на основании `birthDate` и даты, относительно которой выполняется расчёт.

Например:

```text

ph_person_age
```

### Справочник `gender`

| Код | Значение |
| --- | -------- |
| `F` | Женский  |
| `M` | Мужской  |

### Справочник `maritalStatus`

| Код             | Значение           |
| --------------- | ------------------ |

| `MARRIED`       | Состоит в браке    |
| `DIVORCED`      | Разведён(а)        |

| `UNKNOWN`       | Неизвестно         |
| `NOT_SPECIFIED` | Не указано         |

## 12.7. Organization

`Organization` содержит сведения о юридическом лице или иной организации.

| Атрибут                 | Тип    | Описание                      |
| ----------------------- | ------ | ----------------------------- |
| `legalForm`             | string | Организационно-правовая форма |
| `shortName`             | string | Краткое наименование          |
| `fullName`              | string | Полное наименование           |
| `countryOfRegistration` | string | Страна регистрации            |
| `inn`                   | string | ИНН                           |
| `kpp`                   | string | КПП                           |
| `ogrn`                  | string | ОГРН                          |
| `okpo`                  | string | ОКПО                          |
| `bik`                   | string | БИК                           |
| `externalId`            | string | Внешний идентификатор         |

`bik` является необязательным атрибутом, поскольку БИК относится к банковским реквизитам и может отсутствовать у организации.

## 12.8. Document

`Document` содержит сведения о документе, связанном с соответствующим объектом или участником договора.

| Атрибут          | Тип     | Описание                                          |
| ---------------- | ------- | ------------------------------------------------- |
| `typeCode`       | string  | Тип документа                                     |
| `serial`         | string  | Серия документа                                   |
| `number`         | string  | Номер документа                                   |
| `dateIssue`      | date    | Дата выдачи                                       |
| `validTo`        | date    | Дата окончания действия                           |
| `whom`           | string  | Кем выдан                                         |
| `departmentCode` | string  | Код подразделения                                 |
| `countryCode`    | string  | Код страны документа                              |
| `isPrimary`      | boolean | Признак основного документа в транспортной модели |
| `externalId`     | string  | Внешний идентификатор                             |

В канонической модели `isPrimary` и транспортный `externalId` не являются частью бизнес-описания документа.

Для канонической модели выбирается конкретный `document`, соответствующий бизнес-контексту.

Для документов, удостоверяющих личность, `typeCode` должен быть сопоставлен со справочником видов документов, удостоверяющих личность, например СПДУЛ ФНС.

Для других видов документов используются соответствующие справочники платформы.

Важно разделять:

* документы, удостоверяющие личность;
* документы, подтверждающие квалификацию;
* регистрационные документы организации;
* документы транспортного средства;
* иные документы.

Не следует использовать один внешний классификатор как универсальный справочник всех типов документов.

## 12.12. Insured Object

`InsuredObject` описывает объект страхования и связанные с ним параметры.

* груз;
* имущество;
* электронное устройство;
* путешествие;
* иной объект.

Общая структура:

```text
InsuredObject
├── person?
├── organization?
├── document?
├── address?

├── email?
├── vehicle?
├── vehicleDocument?
├── vehicleOwner?
├── drivers[]
├── cargo?
├── carrier?
├── transport[]
├── delivery?
├── vessel?
├── consumerElectronics?
├── flightSegments[]
├── packageCode?
├── sumInsured?
├── deductibleCode?
├── premiumTotal?
├── covers[]
├── cascoAttributes?
├── accidentAttributes?
├── medicalAttributes?
├── cargoAttributes?
└── ...future *Attributes
```

Состав конкретного `InsuredObject` определяется продуктом и его версией.

## 12.13. Party

`Party` в канонической модели представляет сторону или участника страхового контекста.

При этом каноническая модель не содержит транспортных ссылок:

```text
partyId
masterPartyId
```

Эти поля относятся к транспортному протоколу и обрабатываются до формирования канонической модели.

Если транспорт содержит ссылку:

```json
"party": {
  "partyId": "CP-010",
  "masterPartyId": "PARTY-010"
}
```

она должна быть разрешена до mapping в полный объект `Party`.

После разрешения в каноническую модель передаются непосредственно бизнес-данные:

```text
Party
├── person / organization
├── document
├── address
├── phone
└── email
```

`partyId` и `masterPartyId` не должны становиться частью формульного пространства канонической модели.

## 12.14. packageCode, страховая сумма, премия и франшиза

### 12.14.1. packageCode

`packageCode` определяет выбранный пакет страхования.

Пакет является частью конфигурации конкретной версии страхового продукта.

Он может определять:

* набор покрытий;
* набор рисков;
* доступные опции;
* тариф;
* лимиты;
* правила андеррайтинга;
* обязательность дополнительных данных;
* печатные формы и документы.

В контракте передаётся код:

```text
io_packageCode
```

а не копия конфигурации пакета.

Например:

```json
"packageCode": "21"
```

Изменение конфигурации опубликованного продукта не должно изменять уже оформленный договор. Для этого используется версия продукта, с которой был оформлен договор.

---

### 12.14.2. sumInsured

`sumInsured` на уровне `InsuredObject` представляет общую страховую сумму или общий лимит ответственности объекта.

```text
io_sumInsured
```

Например:

```json
"sumInsured": 2627469
```

Отдельное покрытие также может иметь собственную страховую сумму:

```text
covers[].sumInsured
```

Таким образом, необходимо различать:

* общую страховую сумму объекта;
* страховую сумму или лимит конкретного покрытия.

---

### 12.14.3. premiumTotal

`premiumTotal` является результатом расчёта.

```text
io_premiumTotal
```

Он представляет общую страховую премию по объекту.

Если премия рассчитывается по отдельным покрытиям:

```text
premiumTotal = Σ covers[].premium
```

`premiumTotal` не является самостоятельным тарифным параметром.

---

### 12.14.4. deductibleCode

Франшиза задаётся кодом:

```text
deductibleCode
```

Использование отдельного объекта `deductible` не требуется.

Код франшизы связывает контракт с соответствующей конфигурацией продукта.

На уровне `InsuredObject`:

```text
io_deductibleCode
```

На уровне покрытия:

```text
covers[].deductibleCode
```

Размер, тип и правила применения франшизы определяются конфигурацией продукта по соответствующему коду.

---

### 12.14.5. Наследование deductibleCode

Для покрытия действует правило:

```text
Coverage.deductibleCode != null
    → используется deductibleCode покрытия

Coverage.deductibleCode == null
    → используется InsuredObject.deductibleCode
```

Таким образом, покрытие может переопределить общую франшизу объекта.

---

### 12.14.6. Параметры покрытия

Каждое покрытие относится к конфигурации конкретной версии продукта.

Покрытие может определять:

* страховую сумму;
* набор рисков;
* выбранную опцию;
* франшизу;
* страховую премию.

---

### 12.14.7. covers

`covers[]` является частью `InsuredObject`.

```text
InsuredObject
└── covers[]
    ├── coverCode
    ├── option
    ├── sumInsured
    ├── risks[]
    ├── deductibleCode?
    └── premium
```

| Атрибут          | Тип      | Описание                                              |
| ---------------- | -------- | ----------------------------------------------------- |
| `coverCode`      | string   | Код страхового покрытия                               |
| `option`         | string   | Код выбранной опции покрытия                          |
| `sumInsured`     | number   | Страховая сумма или лимит ответственности по покрытию |
| `risks`          | string[] | Коды страховых рисков                                 |
| `deductibleCode` | string   | Код франшизы покрытия                                 |
| `premium`        | number   | Страховая премия по покрытию                          |

`risks` является простым массивом кодов:

```json
{
  "coverCode": "CASCO_DAMAGE",
  "risks": [
    "ACCIDENT",
    "THEFT",
    "FIRE"
  ]
}
```

Отдельный объект `Risk` для данной модели не требуется.

Конкретный набор характеристик определяется соответствующим продуктом.

## 12.25. Flight Segments

Для страхования пассажира и путешествий перелёт может состоять из нескольких сегментов.

Поэтому `flightSegments[]` является массивом в канонической модели.

```text
InsuredObject
└── flightSegments[]
```

| Атрибут             | Тип      | Описание                 |
| ------------------- | -------- | ------------------------ |
| `ticketPrice`       | number   | Стоимость билета         |
| `currencyCode`      | string   | Валюта стоимости         |
| `departureAirport`  | string   | Аэропорт отправления     |
| `arrivalAirport`    | string   | Аэропорт прибытия        |
| `departureDateTime` | datetime | Дата и время отправления |
| `arrivalDateTime`   | datetime | Дата и время прибытия    |
| `airline`           | string   | Авиакомпания             |

Каждый элемент представляет отдельный сегмент путешествия.

---

## 12.26. Специализированные атрибуты страхования

Базовая модель `InsuredObject` содержит общие бизнес-объекты.

Специфические для конкретного вида страхования параметры представлены отдельными объектами `*Attributes`.

Общий принцип:

```text
InsuredObject
├── common data
├── common objects
├── cascoAttributes?
├── accidentAttributes?
├── medicalAttributes?
├── cargoAttributes?
└── future *Attributes
```

Отдельный универсальный контейнер:

```text
programAttributes
```

не используется.

Новый вид страхования добавляет собственный именованный объект:

```text
propertyAttributes
petAttributes
travelAttributes
...
```

Такой подход позволяет расширять модель без изменения семантики общих объектов.

---

## 12.27. CascoAttributes

`cascoAttributes` содержит параметры, специфичные для каско.

| Атрибут             | Тип     | Описание                       |
| ------------------- | ------- | ------------------------------ |
| `coverageTerritory` | string  | Территория страхового покрытия |
| `isAutostart`       | boolean | Признак наличия автозапуска    |
| `purpose`           | string  | Код цели использования         |
| `usingType`         | string  | Код типа использования         |

Пример:

```json
"cascoAttributes": {
  "coverageTerritory": "RU",
  "isAutostart": false,
  "purpose": "3",
  "usingType": "4"
}
```

---

## 12.28. AccidentAttributes

`accidentAttributes` содержит параметры, специфичные для страхования от несчастных случаев.

Для такого продукта `insuredObject` может представлять непосредственно застрахованное физическое лицо.

Концептуально:

```text
InsuredObject
├── person
├── document
├── address
├── phone
├── email
└── accidentAttributes
```

Отдельный объект `insuredPerson` не требуется.

---

## 12.29. MedicalAttributes

`medicalAttributes` содержит параметры, специфичные для медицинского страхования.

Застрахованное лицо также может быть представлено непосредственно через `Person` внутри `InsuredObject`.

```text
InsuredObject
├── person
├── document
├── address
├── phone
├── email
└── medicalAttributes
```

---

## 12.30. CargoAttributes

`cargoAttributes` содержит параметры, специфичные для конкретного продукта страхования груза.

Он является специализированным расширением, а не универсальным контейнером для произвольных параметров.

Общие объекты:

```text
cargo
carrier
transport[]
delivery
```

остаются самостоятельными элементами `InsuredObject`.

---

## 12.32. Дефолтная транспортная модель

Дефолтная транспортная модель предназначена для внешнего API и обмена данными с каналами продаж.

Она может быть более подробной и менее нормализованной, чем каноническая модель.

Основные особенности:

* допускает массивы там, где каноническая модель содержит единичное значение;
* содержит transport metadata;
* может содержать ссылки на Master Data;
* может содержать внешние идентификаторы;
* может быть адаптирована под требования внешнего API.

Дефолтная транспортная модель не является канонической моделью бизнеса.

---

## 12.33. Transport metadata

К транспортным метаданным относятся:

```text
partyId
masterPartyId
isPrimary
externalId
```

Они используются для передачи и разрешения данных, но не являются частью канонической семантики страхового контракта.

### partyId

`partyId` идентифицирует Party в транспортном контексте.

### masterPartyId

`masterPartyId` указывает на источник Master Data, из которого должны быть получены данные Party.

Если `masterPartyId` заполнен, перед mapping ссылка должна быть разрешена в соответствующий объект Master Data.

После разрешения в каноническую модель передаются сами бизнес-данные.

Каноническая модель не должна выполнять динамическое повторное разрешение `masterPartyId`.

Для уже созданного договора данные являются snapshot.

---

## 12.34. Транспортные массивы

Транспортный протокол может использовать массивы для сущностей, которые в канонической модели представлены одним значением.

Например:

```text
Transport
└── policyHolder
    ├── documents[]
    ├── addresses[]
    ├── phones[]
    └── emails[]
```

Каноническая модель:

```text
PolicyHolder
├── document
├── address
├── phone
└── email
```

Такое различие позволяет транспортному API принимать несколько вариантов данных, не усложняя внутреннюю модель.

---

## 12.35. isPrimary

`isPrimary` является транспортным атрибутом.

Он используется, когда транспортная модель содержит несколько экземпляров объекта, а канонической модели требуется одно значение.

Например:

```json
"phones": [
  {
    "typeCode": "MOBILE",
    "value": "79211112233",
    "isPrimary": true
  },
  {
    "typeCode": "WORK",
    "value": "74951234567",
    "isPrimary": false
  }
]
```

Mapping выбирает:

```text
phone = "79211112233"
```

`isPrimary` не является частью канонического атрибута `phone`.

Аналогично механизм может использоваться для:

* документов;
* адресов;
* телефонов;
* email.

Не следует автоматически добавлять `isPrimary` ко всем массивам.

Например, `drivers[]`, `transport[]` и `flightSegments[]` являются множественными бизнес-объектами, а не набором альтернатив одного значения.

---

## 12.36. externalId

`externalId` используется транспортным протоколом для связи передаваемого объекта с внешней системой.

Он может присутствовать, например, у:

* Party;
* Document;
* Address;
* Phone;
* Email.

`externalId` не является формульным идентификатором канонической модели.

Если внешний идентификатор необходим для интеграционного процесса, он должен сохраняться в транспортном или интеграционном контексте.

---

## 12.37. Mapping транспортной модели

Mapping является частью описания транспортной модели.

Его задача — преобразовать входные данные транспортного протокола в каноническую модель.

Общий процесс:

```text
Transport JSON
      ↓
Resolve transport references
      ↓
Select required elements
      ↓
Transform values
      ↓
Canonical Model
```

Например:

```text
policyHolder.phones[]
        ↓
isPrimary = true
        ↓
policyHolder.phone
```

или:

```text
policyHolder.party.masterPartyId
        ↓
Master Data lookup
        ↓
full Party
        ↓
canonical PolicyHolder
```

---

## 12.38. JSONPath в mapping

Для описания соответствия транспортных данных канонической модели используется JSONPath.

Например:

```text
Transport JSONPath
$.policyHolder.person.birthDate
        ↓
Canonical code
ph_person_birthDate
```

Другой пример:

```text
$.policyHolder.phones[?(@.isPrimary == true)].value
        ↓
ph_phone
```

Для документов:

```text
$.policyHolder.documents[?(@.isPrimary == true)]
        ↓
ph_document
```

Таким образом, mapping связывает:

```text
JSONPath
    ↓
Canonical Code
```

а не:

```text
JSONPath
    ↓
Formula
```

Формулы работают только с каноническими кодами.

---

## 12.39. Пример mapping

Для транспортной модели:

```json
{
  "policyHolder": {
    "party": {
      "partyId": "CP-010",
      "masterPartyId": "PARTY-010"
    },
    "person": {
      "firstName": "Иван",
      "lastName": "Иванов",
      "birthDate": "1990-01-10"
    },
    "documents": [
      {
        "typeCode": "PASSPORT",
        "number": "123456",
        "isPrimary": true
      }
    ],
    "phones": [
      {
        "typeCode": "MOBILE",
        "value": "79211112233",
        "isPrimary": true
      }
    ],
    "emails": [
      {
        "typeCode": "WORK",
        "value": "test@example.com",
        "isPrimary": true
      }
    ]
  }
}
```

mapping может выглядеть концептуально следующим образом:

| Transport JSONPath                            | Canonical code        | Правило                   |
| --------------------------------------------- | --------------------- | ------------------------- |
| `$.policyHolder.person.firstName`             | `ph_person_firstName` | Прямое копирование        |
| `$.policyHolder.person.lastName`              | `ph_person_lastName`  | Прямое копирование        |
| `$.policyHolder.person.birthDate`             | `ph_person_birthDate` | Прямое копирование        |
| `$.policyHolder.documents[?(@.isPrimary)].*`  | `ph_document`         | Выбор основного документа |
| `$.policyHolder.phones[?(@.isPrimary)].value` | `ph_phone`            | Выбор основного телефона  |
| `$.policyHolder.emails[?(@.isPrimary)].value` | `ph_email`            | Выбор основного email     |

До выполнения mapping:

```text
masterPartyId
      ↓
Master Data
      ↓
Party data
```

После разрешения ссылка не требуется для расчётной модели.

---

## 12.40. Канонические коды и формулы

Канонические коды используются в формулах как стабильные ссылки на бизнес-атрибуты.

Например:

```text
ph_person_age
ph_person_birthDate
pl_durationYears
io_sumInsured
io_vehicle_vin
```

Формула не должна зависеть от JSONPath транспортного API.

Например, вместо:

```text
$.policyHolder.person.age > 25
```

используется:

```text
ph_person_age > 25
```

Преимущество такого подхода состоит в том, что транспортная модель может изменяться без необходимости изменения формул.

Например, следующие транспортные модели могут приводить к одному каноническому значению:

```text
Transport v1
    ↓
ph_person_age

Transport v2
    ↓
ph_person_age

Internal import
    ↓
ph_person_age
```

---

## 12.41. Snapshot и Master Data

Если транспортная модель содержит ссылку на Master Data, она используется для первоначального получения данных.

Например:

```text
masterPartyId
      ↓
Master Party
      ↓
Transport object
      ↓
Canonical model
      ↓
Quote / Policy
```

После формирования договора данные должны рассматриваться как snapshot договора.

Изменение Master Data не должно автоматически изменять ранее оформленный договор.

Поэтому:

```text
Master Data
```

и

```text
Policy Snapshot
```

являются разными понятиями.

`masterPartyId` является указателем на источник данных, а не механизмом runtime-наследования.

---

## 12.42. Quote и Policy

Если входные бизнес-данные для предварительного расчёта и последующего оформления договора совпадают, нет необходимости создавать две разные модели входного контракта только из-за различия операций.

В этом случае может использоваться общий входной объект:

```text
InsuranceContractRequest
```

Он может использоваться для:

```text
POST /quotes
POST /policies
```

При этом Quote и Policy остаются разными ресурсами и имеют разный lifecycle.

Различие находится на уровне процесса и результата операции, а не обязательно на уровне входной модели.

## 12.44. Разделение ответственности моделей

Архитектурно модели разделяются следующим образом:

```text
                    ┌─────────────────────────┐
                    │   External Transport    │
                    │                         │
                    │ arrays                  │
                    │ partyId                 │
                    │ masterPartyId            │
                    │ isPrimary                │
                    │ externalId               │
                    └────────────┬────────────┘
                                 │
                              Mapping
                                 │
                                 ↓
                    ┌─────────────────────────┐
                    │    Canonical Model      │
                    │                         │
                    │ business semantics       │
                    │ unique codes             │
                    │ normalized values        │
                    └────────────┬────────────┘
                                 │
                 ┌───────────────┼───────────────┐
                 ↓               ↓               ↓
             Calculator        Rules           Policy
```

Таким образом:

* **transport model** отвечает за обмен;
* **mapping** отвечает за преобразование;
* **canonical model** отвечает за бизнес-семантику;
* **calculator** и **rules** работают с canonical codes;
* **policy** хранит результат применения бизнес-модели.

## 12.45. Принципы расширения модели

При добавлении нового страхового продукта сначала определяется, можно ли выразить его через существующие элементы канонической модели.

Если существующих элементов недостаточно, применяются следующие правила.

### Новая общая сущность

Если объект имеет самостоятельный бизнес-смысл и может использоваться несколькими продуктами, он добавляется в базовую модель.

Например:

```text
vehicle
cargo
transport
delivery
flightSegments
consumerElectronics
```

### Специфичный набор параметров продукта

Если параметры относятся только к конкретному виду страхования, используется отдельное расширение:

```text
cascoAttributes
accidentAttributes
medicalAttributes
cargoAttributes
```

### Новое страховое направление

Для нового вида страхования добавляется новый именованный объект:

```text
propertyAttributes
petAttributes
travelAttributes
...
```

Универсальный контейнер `programAttributes` не используется.

---

## 12.46. Каноническая модель как source of truth

Для бизнес-семантики страхового контракта source of truth является каноническая модель.

Транспортный API может изменяться независимо от неё.

Например:

```text
Transport v1 ──┐
               ├──→ Canonical Model
Transport v2 ──┤
               │
Internal API ──┘
```

Это позволяет нескольким внешним протоколам использовать одну бизнес-модель.

При этом транспортные версии могут развиваться независимо:

```text
Canonical Model
      ↑
      │
 ┌────┴─────┐
 │          │
v1         v2
Transport  Transport
```

В текущем разделе описывается **дефолтная транспортная модель и её mapping**.

Если в дальнейшем появится новый транспортный контракт с существенно отличающейся структурой или правилами обмена, он должен быть описан отдельным разделом/главой **«Транспортная модель v2»**, не изменяя семантику канонической модели.

---

## 12.47. Итоговая модель

Итоговое разделение ответственности:

```text
                    INSURANCE CONTRACT
                           │
             ┌─────────────┴─────────────┐
             │                           │
             ↓                           ↓
      Canonical Model             Transport Model
             │                           │
             │                      API / Integration
             │                           │
             │                       Mapping
             │                           │
             └─────────────┬─────────────┘
                           ↓
                    Business Processing
                           │
                 ┌─────────┼─────────┐
                 ↓         ↓         ↓
             Calculator  Rules     Policy
```

Ключевой принцип модели:

> **Каноническая модель описывает бизнес-смысл страхового контракта. Транспортная модель описывает способ передачи этого контракта. Mapping связывает транспортные данные с каноническими кодами.**

Поэтому изменение JSON-структуры внешнего API не должно само по себе приводить к изменению формул, правил и бизнес-семантики страхового договора.


# 17. Документы и файловое хранилище

pt-files отвечает за файловый контур. В текущей технологии используются MinIO и PDFBox.

```text
Business document
       |
       v
Document metadata
       |
       +------> Object Storage (MinIO)
       |
       +------> PDF generation / processing (PDFBox)

```

Важно разделять документ как бизнес-сущность и файл как бинарный объект. Policy может иметь несколько документов, а один document record должен иметь понятный lifecycle и связь с бизнес-объектом.
Email-зависимости присутствуют в backend-контексте, однако точная схема notification service в текущем источнике не зафиксирована.

# 18. Номера и идентификаторы

pt-numbers отвечает за генерацию бизнес-номеров. В контексте зафиксирована поддержка placeholder-формата и reset policies, а для последовательностей упоминается pessimistic locking.

## Разные виды идентификаторов


Идентификатор | Назначение

|---|---|

|Technical ID|Внутренний уникальный идентификатор сущности|

|Business number|Номер полиса/документа, видимый бизнесу|

|partyId|Идентификатор Party snapshot|

|masterPartyId|Источник Party в Master Data|

|productCode|Код продукта|

Business number и technical ID не должны смешиваться. Номер полиса может иметь бизнес-правила генерации и форматирование, тогда как technical ID должен оставаться стабильным техническим ключом.

# 19. Платежи и комиссии

Модуль pt-payments существует в текущем backend. Однако конкретный payment provider и полный lifecycle в предоставленном контексте не зафиксированы.

```text
Policy / Invoice
      |
      v
Payment Created
      |
      v
Provider / payment channel
      |
      v
Result
      |
      +--> success
      +--> failure
      +--> refund

```

Для финансовых операций рекомендуется обеспечивать идемпотентность, correlation ID и явное хранение provider reference. Эти пункты относятся к архитектурным требованиям, если соответствующий финансовый workflow будет реализован.
Комиссии также присутствуют как доменная область, но точная схема settlement не подтверждена текущим контекстом.

# 20. Claims и незавершённые области

В контексте присутствует privilege для claims, однако отдельного pt-claims модуля нет. Следовательно, claims следует считать частично определённой/незавершённой областью, а не готовым самостоятельным bounded context.
Шаблон CONTEXT.md содержит типовой FNOL/Claims lifecycle, но он не является доказательством реализации в текущем репозитории.

## Event-driven architecture

В pt-process обнаружена зависимость jakarta.jms-api, а ActiveMQ starter присутствует в закомментированном виде. Это указывает на возможный процессный/event-driven контур, но не подтверждает работающий message broker в production.

# 21. API и интеграционные границы

REST API является основным внешним контрактом backend; Springdoc OpenAPI используется для описания API.

## Ключевой принцип

API DTO не должны быть зеркалом database entities. Они описывают внешний бизнес-контракт.

## Quote / Policy

Если входные поля одинаковы, допустимо использовать общий InsuranceContractRequest. Разные response/resource модели при этом остаются нормальными.

## Идемпотентность

Для критических операций, особенно выпуска полиса и финансовых действий, необходимо иметь явную стратегию идемпотентности. Конкретный реализованный механизм следует подтверждать endpoint-кодом.

# 22. Данные, миграции и Source of Truth

PostgreSQL является центральным persistent storage. JPA используется для persistence, а миграции в текущем контексте выполняются Flyway.

## Source of truth hierarchy


Уровень | Вес

|---|---|

|Текущий исходный код|Максимальный|

|DB migrations|Очень высокий|

|Runtime/config|Высокий|

|Tests|Высокий|

|API contracts|Высокий|

|Текущая документация|Средний|

|Исторический README / vision|Низкий|

Если документация расходится с кодом, документ должен быть исправлен или явно помечен как proposed. Нельзя незаметно подменять реализованную архитектуру желаемой.

## Data model vs business model

Business JSON contract документируется отдельно от JPA/DB схемы. Это позволяет менять storage без изменения внешнего API.

# 24. Observability и эксплуатация

Spring Boot Actuator присутствует в backend и предоставляет health endpoint. Полный production stack логирования, tracing, metrics backend и alerting в текущем контексте не определён.

## Минимальный эксплуатационный контур

- Health/readiness проверки.

- Structured application logs.

- Correlation ID для межмодульных операций.

- Метрики API и расчёта.

# 25. Архитектурные принципы

- <b>Business model first.</b> Сначала фиксируется смысл сущности, затем DTO и persistence.

- <b>Immutable product versions.</b> Published Product Version не меняется задним числом.

- <b>Policy snapshot.</b> Полис сохраняет данные, использованные при оформлении.

- <b>Master Data is provenance.</b> masterPartyId — источник, а не runtime inheritance.

- <b>Tenant isolation server-side.</b> Нельзя полагаться только на tenantId из URL.

- <b>Privilege + scope.</b> Permission и область данных — разные измерения доступа.

- <b>Extensible InsuredObject.</b> Новые страховые типы добавляют специализированный *Attributes блок.

- <b>No generic programAttributes.</b> Специализация должна быть явно именована.

- <b>Transport is a list.</b> Мультимодальная перевозка требует массива transport[].

- <b>Documents are not identifiers.</b> INN/KPP/OGRN/SNILS — реквизиты, а не документы.

- <b>Modular monolith first.</b> Модули разделяют ответственность без преждевременного перехода к микросервисам.
