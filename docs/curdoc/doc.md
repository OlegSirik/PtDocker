# 1. Назначение и границы платформы

Платформа предназначена для автоматизации страхового бизнеса: управления страховыми продуктами, расчёта стоимости, подготовки и выпуска страховых договоров, хранения документов, работы с платежами и поддержки дополнительных страховых процессов.
В текущем техническом контексте платформа строится как единое backend-приложение с модульным разделением ответственности. Это позволяет сохранять единый транзакционный контур и одновременно разделять домены на уровне Java-модулей.

## Что является центральным объектом

Центральным бизнес-объектом выступает страховой контракт/полис. Он связывает продукт, застрахованный объект, участников договора, покрытия, тарифные параметры, документы и финансовые данные.

## Граница ответственности

- Продукт определяет, что и на каких условиях страхуется.

- Calculator вычисляет стоимость на основе тарифных данных и формул.

- Rules применяет бизнес-правила и проверки.

- Policy фиксирует результат оформления как исторический snapshot.

- Files отвечает за документы и объектное хранилище.

- Payments содержит финансовый контур; точный provider lifecycle требует дальнейшей фиксации.

# 2. Архитектурный стиль

Текущая архитектура определяется как modular monolith: один backend runtime, внутри которого существуют отдельные Gradle-модули с собственными зонами ответственности.

```text
Client / Browser / Partner
          |
          v
      HTTP API
          |
          v
+-----------------------------------------------+
|                 Backend                       |
|                                               |
| api | auth | product | calculator | rules    |
| process | numbers | files | payments | db    |
+-----------------------+-----------------------+
                        |
                        v
                   PostgreSQL

```


## Почему модульный монолит

- Единая транзакционная модель для критических страховых операций.

- Меньше инфраструктурной сложности, чем у набора микросервисов.

- Явные границы доменов можно сохранить внутри кода.

- При необходимости отдельный модуль впоследствии может стать самостоятельным сервисом.

Микросервисная декомпозиция не должна считаться текущим фактом. Она может быть будущей эволюцией, но не является описанием сегодняшнего runtime.

# 5. Frontend и пользовательский интерфейс

Frontend построен на Angular/TypeScript. В текущем контексте используются Angular Router, Angular Material, Formly, RxJS, Chart.js и интеграция с Keycloak.
Маршрутизация содержит tenantId как часть URL-контекста. Это важно: tenant является не только внутренним параметром backend, но и частью пользовательского контекста frontend.

```text
/:tenantId/...
       |
       +-- authGuard
       |
       +-- TenantGuard
       |
       +-- tenant-scoped application UI

```

Таким образом, frontend должен передавать и поддерживать tenant context, а backend обязан независимо проверять принадлежность текущего principal к tenant scope. Нельзя считать URL единственным механизмом изоляции.

# 6. Аутентификация

Аутентификация отвечает на вопрос: кто выполняет запрос? В проекте присутствует Keycloak-конфигурация и JWT-инфраструктура. Точная граница ответственности между Keycloak и приложением должна быть подтверждена текущими security-конфигурациями и deployment setup.

## Концептуальный поток


```text
User / Client
     |
     | credentials / SSO
     v
 Identity Provider (Keycloak)
     |
     | access token
     v
 Frontend
     |
     | Authorization: Bearer <token>
     v
 Backend / Spring Security
     |
     +--> validate token
     +--> resolve Principal
     +--> resolve Account / tenant context

```


## Что не следует смешивать

- Authentication — проверка личности/credentials.

- Authorization — проверка разрешений.

- Tenant isolation — проверка области данных.

- Acting account — контекст, от имени которого выполняется операция.

Даже валидный JWT не должен автоматически давать доступ ко всем данным платформы.

# 7. Авторизация

В текущей модели авторизация строится не только вокруг ролей. Зафиксирована комбинация Account hierarchy, explicit privileges и data scope.

## Privilege

Privilege имеет формат &lt;RESOURCE&gt;:&lt;ACTION&gt;. Примеры концептуально: POLICY:READ, POLICY:CREATE, PRODUCT:UPDATE.

## Account и Acting Account

Account представляет субъект/организационный контекст доступа. Acting Account позволяет явно фиксировать, от имени какого аккаунта выполняется действие, что особенно важно при иерархии организаций, брокеров, агентов и дочерних аккаунтов.

## Модель проверки


```text
Request
  |
  v
Authenticated Principal
  |
  +--> Is authenticated?
  |
  +--> Which Account?
  |
  +--> Which Acting Account?
  |
  +--> Has required Privilege?
  |
  +--> Is resource inside Data Scope?
  |
  v
Allow / Deny

```

Privilege отвечает на вопрос <i>что можно сделать</i>, а data scope — <i>с какими данными можно это сделать</i>.

Продукт является конфигурацией страхового предложения. Внутри него находятся версии, покрытия, риски, тарифные таблицы, формулы, правила и документы.

```text
Product Family / Group
          |
          v
       Product
          |
          +---- Product Version
                    |
          +---------+---------+---------+
          |         |         |         |
       Coverages  Risks    Rates      Rules
                                                                     +-- Formulas

```


## Версионирование

Опубликованная Product Version не должна изменяться задним числом. Lifecycle: DRAFT → PUBLISHED → DEPRECATED.
Это необходимо для воспроизводимости расчёта и исторической корректности полиса: старый договор должен ссылаться на ту версию продукта, на которой он был оформлен.

## Quote

Quote — результат предварительного расчёта и предложения. Его задача — показать условия и стоимость до окончательного выпуска.

## Policy

Policy — зафиксированный страховой договор. Для него критична историческая неизменяемость исходных данных: Party и Insured Object сохраняются как snapshot.

## Snapshot semantics

Если Party была создана на основе Master Data через masterPartyId, изменение Master Data после выпуска полиса не должно менять уже существующий полис.

# 12. Страховой контракт

Страховой контракт — общий бизнес-контракт для расчёта и оформления. Он включает productCode, даты, валюту, тип рассрочки, policyHolder и insuredObject.

# 12. Страховой контракт

## 12.1. Назначение страхового контракта

Страховой контракт является общим бизнес-контрактом системы для выполнения операций, связанных с расчётом и оформлением страхового продукта.

Контракт описывает страхуемую ситуацию в терминах предметной области: кто заключает договор, что является объектом страхования, какие документы и дополнительные сведения относятся к объекту, а также какие параметры конкретного страхового продукта применяются.

Модель контракта не должна повторять внутреннюю структуру базы данных. JSON-контракт является **business model**, предназначенной для взаимодействия между клиентом, API и бизнес-логикой системы. JPA Entity, таблицы базы данных и другие технические структуры являются **implementation model** и могут иметь другую структуру.

Общая модель должна быть достаточно универсальной, чтобы один и тот же контракт мог использоваться для разных видов страхования: например, автомобиля, человека, груза, транспортного средства, пассажирской поездки или бытовой электроники.

При этом конкретный страховой продукт определяет, какие части модели являются обязательными и какие специализированные данные должны быть представлены.

---

## 12.2. Концепция модели

Модель страхового контракта строится по принципу разделения на несколько уровней:

1. общие атрибуты контракта;
2. типовые объекты и участники;
3. застрахованный объект;
4. специализированные объекты;
5. специализированные атрибуты конкретного вида страхования;
6. покрытия и риски, определяемые страховым продуктом.

Упрощённо структура выглядит следующим образом:

```text
Contract
├── Header
│   ├── productCode
│   ├── startDate
│   ├── endDate
│   ├── issueDate
│   ├── currencyCode
│   └── installmentType
│
├── policyHolder
│
└── insuredObject
    ├── common data
    ├── party / person / organization
    ├── documents[]
    ├── addresses[]
    ├── phones[]
    ├── emails[]
    │
    ├── vehicle?
    ├── cargo?
    ├── transport[]?
    ├── delivery?
    ├── consumerElectronics?
    ├── flightSegments[]?
    │
    ├── packageCode?
    ├── sumInsured?
    │
    ├── cascoAttributes?
    ├── accidentAttributes?
    ├── medicalAttributes?
    └── cargoAttributes?
```

Не все элементы присутствуют одновременно. Набор данных определяется конкретным страховым продуктом.

Такой подход позволяет не создавать отдельную модель договора для каждого продукта. Вместо этого используется единый контракт, который расширяется необходимыми предметными объектами и специализированными атрибутами.

## 12.3 Правило модели

isPrimary определяет основной элемент соответствующего массива в контексте конкретной роли. Наличие нескольких элементов допускается, при этом конкретный бизнес-сценарий может требовать наличие одного основного элемента.

То есть:

Массив	isPrimary
documents[]	основной документ
addresses[]	основной адрес
phones[]	основной телефон
emails[]	основной email

При этом typeCode и isPrimary решают разные задачи:

typeCode — что это за элемент;
isPrimary — какой элемент является основным.

Например, typeCode = LEGAL не обязательно означает isPrimary = true: у организации может быть несколько адресов, и бизнес-логика отдельно определяет, какой из них основной.

## 12.3. Шапка договора

Шапка договора содержит общие параметры страхового контракта, которые не относятся непосредственно к конкретному застрахованному объекту.

| Поле              | Назначение                                  |
| ----------------- | ------------------------------------------- |
| `productCode`     | Код страхового продукта                     |
| `startDate`       | Дата и время начала действия страхования    |
| `endDate`         | Дата и время окончания действия страхования |
| `issueDate`       | Дата и время оформления договора            |
| `currencyCode`    | Валюта денежных значений договора           |
| `installmentType` | Тип рассрочки / схема оплаты                |
| `policyHolder`    | Страхователь                                |

Пример:

```json
{
  "productCode": "FINAUTO_HELP",
  "startDate": "2026-08-19T00:00:00+03:00",
  "endDate": "2027-08-19T00:00:00+03:00",
  "issueDate": "2026-08-19T00:00:00+03:00",
  "currencyCode": "RUR",
  "installmentType": "13",
  "policyHolder": {},
  "insuredObject": {}
}
```

Шапка описывает контекст договора, но не определяет конкретный набор страхуемых объектов. Например, один и тот же набор общих полей может использоваться для договора страхования автомобиля и для договора страхования груза.

---

## 12.4. Policy Holder

`policyHolder` представляет страхователя — участника договора, от имени которого заключается страховой договор.

Страхователь является одним из вариантов использования общей модели `Party`.

В зависимости от продукта страхователем может быть физическое или юридическое лицо.

Структура объекта должна позволять передавать:

* идентификатор Party;
* источник данных Party;
* сведения о физическом лице или организации;
* документы;
* адреса;
* телефоны;
* электронные адреса.

При этом сведения внутри договора являются snapshot данных на момент формирования контракта.

---

## 12.5. Типовые объекты

Типовые объекты являются переиспользуемыми элементами модели. Они не должны зависеть от конкретного страхового продукта.

К ним относятся:

* Party;
* Person;
* Organization;
* Document;
* Address;
* Phone;
* Email.

Эти объекты используются как непосредственно в договоре, так и внутри специализированных объектов.

---

## 12.6. Party

`Party` представляет участника страхового договора или другого предметного объекта.

В договоре Party хранится как snapshot. Это означает, что данные, использованные при оформлении договора, сохраняются внутри самого договора и не должны изменяться автоматически при последующем изменении Master Data.

Для идентификации используются два значения:

| Поле            | Назначение                                                          |
| --------------- | ------------------------------------------------------------------- |
| `partyId`       | Идентификатор Party snapshot внутри договора                        |
| `masterPartyId` | Идентификатор объекта Master Data, из которого были получены данные |

`masterPartyId` является источником происхождения данных, а не механизмом runtime-наследования.

Если `masterPartyId` заполнен, данные Party при создании договора могли быть скопированы из соответствующего объекта Master Data.

После создания договора изменение Master Data не должно автоматически изменять уже существующий договор.

```json
{
  "party": {
    "partyId": "CP-010",
    "masterPartyId": "PARTY-010"
  }
}
```

Одна и та же модель Party может использоваться для разных ролей:

```text
policyHolder
vehicleOwner
driver
carrier
insured object Party
```

`Person` содержит сведения о физическом лице.

Физическое лицо может использоваться как страхователь, застрахованный, водитель или другой участник договора.

## 12.7. Person

## 12.8. Organization

| Атрибут                 | Тип    | Описание                               |
| ----------------------- | ------ | -------------------------------------- |
| `legalForm`             | string | Организационно-правовая форма          |
| `shortName`             | string | Краткое наименование организации       |
| `fullName`              | string | Полное наименование организации        |

| `inn`                   | string | ИНН                                    |
| `kpp`                   | string | КПП                                    |
| `ogrn`                  | string | ОГРН                                   |
| `okpo`                  | string | Код организации по ОКПО                |
| `bik`                   | string | БИК                                    |
| `externalId`            | string | Внешний идентификатор организации      |

`countryOfRegistration` определяет страну регистрации организации. Отдельный атрибут `isResident` в `Organization` не используется: при необходимости признак резидентства должен определяться бизнес-правилами на основании страны регистрации и других необходимых данных.

Для российских организаций `inn`, `kpp`, `ogrn`, `okpo` и `bik` заполняются при наличии соответствующих реквизитов. Для организаций других юрисдикций набор локальных регистрационных и идентификационных реквизитов может отличаться.

Регистрационные документы организации, если они требуются для страхового контракта, хранятся отдельно в `documents[]`.

```json id="p8x4km"
  "countryOfRegistration": "RU",
  "inn": "7705757890",
  "kpp": "770901001",
  "ogrn": "1067757802793",
  "okpo": "12345678",
  "bik": "044525000",
  "externalId": "EXT-ORG-123456"
}
```

## 12.9. Document

`Document` содержит сведения о документе, связанном с участником страхового контракта. Документ может удостоверять личность, подтверждать право управления транспортным средством, регистрацию организации или содержать иные юридически значимые сведения.

| Атрибут          | Тип     | Описание                                                       |
| ---------------- | ------- | -------------------------------------------------------------- |
| `typeCode`       | string  | Тип документа                                                  |
| `serial`         | string  | Серия документа                                                |
| `number`         | string  | Номер документа                                                |
| `dateIssue`      | date    | Дата выдачи документа                                          |
| `validTo`        | date    | Дата, до которой документ действителен                         |
| `whom`           | string  | Орган или организация, выдавшая документ                       |
| `departmentCode` | string  | Код подразделения, выдавшего документ                          |
| `countryCode`    | string  | Страна выдачи документа, ISO 3166-1 alpha-2                    |
| `isPrimary`      | boolean | Признак основного документа в рамках соответствующей коллекции |
| `externalId`     | string  | Внешний идентификатор документа                                |

`typeCode` определяет вид документа, например паспорт, водительское удостоверение или регистрационный документ организации. Для документов, удостоверяющих личность физического лица, используется справочник СПДУЛ ФНС России.
[ Справочник «Виды документов, удостоверяющих личность» (СПДУЛ) ](https://www.nalog.gov.ru/opendata/7707329152-spdul/ )

`isPrimary` используется для обозначения основного документа, когда у одной стороны может быть несколько документов одного или разных типов. Признак относится к конкретной коллекции документов и не заменяет `typeCode`.

`validTo` является необязательным: не все документы имеют установленный срок действия.

`departmentCode` заполняется для документов, в которых предусмотрен код подразделения, например для российского паспорта.

`externalId` предназначен для связи документа с соответствующим объектом во внешней системе.

Пример:

```json
{
  "typeCode": "PASSPORT_RF",
  "serial": "4501",
  "number": "123456",
  "dateIssue": "2015-06-20",
  "validTo": null,
  "whom": "ОТДЕЛОМ УФМС РОССИИ ПО Г. МОСКВЕ",
  "departmentCode": "770-001",
  "countryCode": "RU",
  "isPrimary": true,
  "externalId": "EXT-DOC-123456"
}
```

## 12.10. Address

`Address` содержит структурированные сведения об адресе, а также его идентификаторы в адресных классификаторах. Один `Party` или `InsuredObject` может иметь несколько адресов разных типов.

| Атрибут         | Тип     | Описание                                                    |
| --------------- | ------- | ----------------------------------------------------------- |
| `typeCode`      | string  | Тип адреса                                                  |
| `countryCode`   | string  | Код страны, ISO 3166-1 alpha-2                              |
| `region`        | string  | Регион, область, край, республика и т. п.                   |
| `city`          | string  | Город или населённый пункт                                  |
| `street`        | string  | Улица, переулок, проспект и т. п.                           |
| `house`         | string  | Номер дома                                                  |
| `building`      | string  | Номер строения, корпуса и т. п.                             |
| `apartment`     | string  | Номер квартиры                                              |
| `room`          | string  | Номер комнаты                                               |
| `postalCode`    | string  | Почтовый индекс                                             |
| `kladrCode`     | string  | Код адресного объекта по КЛАДР                              |
| `fiasCode`      | string  | Идентификатор адресного объекта в ФИАС                      |
| `garCode`       | string  | Идентификатор адресного объекта в ГАР                       |
| `addressLine`   | string  | Адресная строка в локальном формате                         |
| `addressLineEn` | string  | Адресная строка на английском языке                         |
| `isPrimary`     | boolean | Признак основного адреса в рамках соответствующей коллекции |
| `externalId`    | string  | Внешний идентификатор адреса                                |

`typeCode` определяет назначение адреса. Например: `LEGAL` — юридический адрес, `REGISTRATION` — адрес регистрации, `RESIDENTIAL` — адрес проживания, `POSTAL` — почтовый адрес, `ORIGIN` — адрес отправления, `DESTINATION` — адрес назначения.

Для одного типа адреса может существовать несколько значений. В этом случае `isPrimary` позволяет указать основной адрес.

`kladrCode`, `fiasCode` и `garCode` используются для идентификации адреса в соответствующих российских адресных классификаторах. Они не являются заменой структурированных компонентов адреса.

Для идентификации адресов могут использоваться несколько российских адресных классификаторов:

* **КЛАДР** (Классификатор адресов Российской Федерации) — более ранняя система классификации адресных объектов, использовавшаяся для кодирования регионов, районов, городов, улиц и других элементов адреса.
* **ФИАС** (Федеральная информационная адресная система) — федеральная система адресных сведений, пришедшая на смену КЛАДР и предоставляющая более детализированную идентификацию адресных объектов.
* **ГАР** (Государственный адресный реестр) — актуальная государственная система ведения сведений об адресах, в которой каждому адресному объекту присваивается уникальный идентификатор. В модели `Address` эти идентификаторы хранятся отдельно, поскольку КЛАДР, ФИАС и ГАР относятся к разным системам и периодам ведения адресных данных. Для новых интеграций приоритетным является использование идентификаторов ГАР.

`addressLine` предназначен для представления адреса в готовом виде, например для отображения или печати в документах. `addressLineEn` содержит представление адреса на английском языке.

Структурированные компоненты адреса (`region`, `city`, `street`, `house`, `building`, `apartment`, `room`) могут отсутствовать, если соответствующий компонент неприменим к конкретному адресу.

Пример:

```json
{
  "typeCode": "LEGAL",
  "countryCode": "RU",
  "region": "г. Москва",
  "city": "Москва",
  "street": "пер Малый Дровяной",
  "house": "3",
  "building": "1",
  "apartment": null,
  "room": null,
  "postalCode": "109004",
  "kladrCode": "7700000000000",
  "fiasCode": "00000000-0000-0000-0000-000000000000",
  "garCode": "00000000-0000-0000-0000-000000000000",
  "addressLine": "109004, г. Москва, пер Малый Дровяной, д. 3, корп. 1",
  "addressLineEn": "3, bld. 1, Maly Drovyanoy Lane, Moscow, 109004, Russia",
  "isPrimary": true,
  "externalId": "EXT-ADDR-123456"
}
```

### Справочник `typeCode`

| Код             | Значение          | Описание                                                    |
| --------------- | ----------------- | ----------------------------------------------------------- |
| `LEGAL`         | Юридический       | Юридический адрес организации                               |
| `REGISTRATION`  | Адрес регистрации | Адрес регистрации физического лица                          |
| `RESIDENTIAL`   | Адрес проживания  | Фактический адрес проживания физического лица               |
| `POSTAL`        | Почтовый          | Адрес для получения корреспонденции                         |
| `ACTUAL`        | Фактический       | Фактический адрес организации                               |
| `TEMPORARY`     | Временный         | Адрес временного пребывания                                 |
| `ORIGIN`        | Отправление       | Адрес отправления груза или иного объекта                   |
| `TRANSSHIPMENT` | Перегрузка        | Адрес промежуточной перегрузки или перевалки                |
| `DESTINATION`   | Назначение        | Адрес назначения груза или иного объекта                    |
| `OTHER`         | Другой            | Иной тип адреса, не предусмотренный стандартными значениями |

Справочник является внутренним справочником модели страхового контракта. Значение `typeCode` определяет бизнес-назначение адреса в конкретном контексте.

Для адресов, относящихся к маршруту перевозки, значения `ORIGIN`, `TRANSSHIPMENT` и `DESTINATION` используются для формирования последовательности точек маршрута. Адресов типа `TRANSSHIPMENT` может быть несколько.

Для одного типа адреса может существовать несколько экземпляров. `isPrimary` позволяет указать основной адрес среди адресов соответствующей коллекции.

## 12.13. Insured Object

`insuredObject` является центральной частью страхового контракта.

Он описывает то, в отношении чего возникает страховой интерес и к чему применяются условия страхового продукта.

В зависимости от продукта застрахованным объектом может быть:

* физическое лицо;
* транспортное средство;
* груз;
* перевозка;
* бытовая электроника;
* пассажирская поездка;
* другой предмет страхования.

`insuredObject` является расширяемой структурой. Общие элементы располагаются непосредственно внутри объекта, а специализированные предметные объекты добавляются как именованные поля.

Пример:

```text
insuredObject
├── party?
├── person?
├── organization?
├── documents[]
├── addresses[]
├── phones[]
├── emails[]
│
├── vehicle?
├── vehicleOwner?
├── drivers[]?
├── cargo?
├── carrier?
├── transport[]?
├── delivery?
├── consumerElectronics?
├── flightSegments[]?
│
├── packageCode?
├── sumInsured?
│
├── cascoAttributes?
├── accidentAttributes?
├── medicalAttributes?
└── cargoAttributes?
```

Не все элементы присутствуют одновременно.

Набор элементов определяется страховым продуктом и его требованиями к данным.

## 12.14. Общие параметры `InsuredObject`

Помимо специализированных данных конкретного объекта страхования, `InsuredObject` содержит общие параметры, которые относятся ко всему объекту в рамках выбранного продукта и страховой программы.

К таким параметрам относятся:

* `packageCode` — выбранная страховая программа (пакет);
* `sumInsured` — страховая сумма или общий лимит ответственности;
* `deductibleCode` — код общей франшизы, применяемой к покрытиям по умолчанию;
* `premiumTotal` — суммарная страховая премия по всем покрытиям объекта;
* `covers[]` — набор покрытий, фактически применённых к объекту.

```text id="r4f8q2"
InsuredObject
├── packageCode
├── sumInsured
├── deductibleCode?
├── premiumTotal
├── covers[]
│   ├── coverCode
│   ├── option
│   ├── sumInsured
│   ├── risks[]
│   ├── deductibleCode?
│   └── premium
└── ...
```

При этом необходимо различать параметры, задаваемые при формировании договора, и расчётные результаты.

`packageCode` и, в зависимости от продукта, `sumInsured` и `deductibleCode` могут являться входными параметрами расчёта. `premiumTotal` является производным расчётным значением: оно формируется на основании премий отдельных покрытий и не должно самостоятельно вводиться как независимое значение.

### 12.14.1. `packageCode`

`packageCode` определяет выбранный пакет или страховую программу внутри конкретного продукта.

Пакет настраивается в конфигурации продукта и определяет набор параметров, применяемых при расчёте и оформлении договора. В частности, конфигурация пакета может определять:

* обязательные покрытия;
* доступные и необязательные покрытия;
* набор страховых рисков;
* тарифные параметры и правила расчёта;
* доступные лимиты и страховые суммы;
* допустимые значения франшиз;
* дополнительные параметры андеррайтинга;
* обязательные данные объекта страхования;
* условия применения скидок и надбавок;
* печатные формы и состав документов;
* другие параметры конкретной страховой программы.

В самом страховом контракте хранится только код выбранного пакета:

```json id="a6z9qk"
{
  "packageCode": "21"
}
```

Контракт не должен дублировать всю конфигурацию пакета. При расчёте или оформлении система использует `packageCode` совместно с `productCode` и версией продукта для определения соответствующей конфигурации.

```text id="p3v7mx"
Product
   │
   └── Product Version
          │
          └── Package
                ├── required coverages
                ├── optional coverages
                ├── tariff configuration
                ├── underwriting rules
                ├── deductible configuration
                ├── document configuration
                └── other product parameters
```

Если конфигурация продукта изменяется таким образом, что это влияет на смысл или расчёт уже существующей программы, изменение должно фиксироваться в новой версии продукта. Оформленный договор сохраняет использованную версию продукта и `packageCode`, чтобы его условия могли быть однозначно восстановлены в дальнейшем.

### 12.14.2. `sumInsured`

`sumInsured` определяет страховую сумму или общий лимит ответственности, относящийся ко всему `InsuredObject`.

Точное бизнес-значение параметра зависит от типа страхового продукта и выбранных покрытий. В классическом варианте `sumInsured` представляет максимальную сумму ответственности страховщика по объекту. Для продуктов, где применяется термин «лимит ответственности», этот же параметр может использоваться как общий лимит ответственности.

```json id="n2w8fc"
{
  "sumInsured": 2627469
}
```

`sumInsured` находится на уровне `InsuredObject`, поскольку может задавать общий финансовый предел для объекта независимо от конкретного покрытия.

При этом отдельное покрытие также может иметь собственную страховую сумму или лимит ответственности:

```text id="c5m1yb"
InsuredObject
├── sumInsured = 2 627 469
│
└── covers[]
    ├── Coverage A
    │   └── sumInsured = 2 000 000
    │
    └── Coverage B
        └── sumInsured = 500 000
```

Таким образом, наличие `sumInsured` на уровне объекта не исключает наличия собственного `sumInsured` на уровне покрытия.

Необходимо различать:

* общую страховую сумму объекта — `InsuredObject.sumInsured`;
* страховую сумму конкретного покрытия — `Coverage.sumInsured`;
* лимит ответственности конкретного покрытия, если по бизнес-смыслу продукта используется именно ограничение ответственности.

Для конкретного продукта может быть определено, какой из этих параметров является обязательным, как они соотносятся между собой и допускается ли сумма покрытия, превышающая общую сумму объекта.

Если значение `sumInsured` рассчитывается системой из других данных объекта, оно является расчётным результатом. Если сумма выбирается пользователем или приходит из внешней системы как параметр договора, она является входным параметром расчёта.

В модели страхового контракта рекомендуется сохранять фактически применённое значение `sumInsured`, использованное при расчёте и оформлении договора.

### 12.14.3. `premiumTotal`

`premiumTotal` — общая страховая премия по `InsuredObject`, рассчитанная как сумма премий отдельных покрытий.

```json id="u7k3pd"
{
  "premiumTotal": 38450.00
}
```

Значение предназначено прежде всего для удобства использования: потребителю API, пользовательскому интерфейсу, печатным формам и другим интеграциям не требуется самостоятельно суммировать премии всех покрытий.

Основным источником значения являются премии отдельных покрытий:

```text id="h9w4kc"
premiumTotal =
    premium(Coverage 1)
  + premium(Coverage 2)
  + ...
  + premium(Coverage N)
```

Например:

```text id="e6p2rs"
Coverage A → premium = 25 000
Coverage B → premium =  8 500
Coverage C → premium =  4 950
                     ─────────
premiumTotal        = 38 450
```

В JSON:

```json id="m8x1qa"
{
  "premiumTotal": 38450.00,
  "covers": [
    {
      "coverCode": "COVERAGE_A",
      "premium": 25000.00
    },
    {
      "coverCode": "COVERAGE_B",
      "premium": 8500.00
    },
    {
      "coverCode": "COVERAGE_C",
      "premium": 4950.00
    }
  ]
}
```

`premiumTotal` не является самостоятельным тарифным параметром. Он не должен использоваться как источник расчёта премий покрытий.

Правильная зависимость выглядит следующим образом:

```text id="k3r7vn"
Product / Product Version
        │
        ├── packageCode
        │
        └── tariff configuration
                │
                ▼
        Calculation by Coverage
                │
        ┌───────┼────────┐
        ▼       ▼        ▼
     Cover A  Cover B  Cover C
     premium  premium  premium
        │       │        │
        └───────┼────────┘
                ▼
          premiumTotal
```

При расчёте система сначала определяет премию каждого применимого покрытия, после чего формирует `premiumTotal`.

Это позволяет одновременно хранить:

1. детализацию расчёта на уровне покрытия;
2. удобный агрегированный итог на уровне `InsuredObject`.

Для уже оформленного договора `premiumTotal` должен соответствовать фактически применённым премиям покрытий. Изменение состава покрытий или их премий должно приводить к соответствующему пересчёту `premiumTotal`.

### 12.14.4. `deductibleCode`

`deductibleCode` определяет общую франшизу, применяемую к покрытиям `InsuredObject` по умолчанию.

```json id="f1q8mz"
{
  "deductibleCode": "FIX300"
}
```

`deductibleCode` является ссылкой на условие франшизы, определённое в конфигурации продукта или соответствующем справочнике.

Например:

```text id="j6p3vx"
FIX300
```

может соответствовать условию:

```text id="b8n5lc"
300 рублей после второго страхового случая
```

В самом страховом контракте хранится только код. Описание, размер франшизы, правила её применения и другие параметры определяются конфигурацией продукта.

Такой подход позволяет:

* не дублировать описание франшизы в каждом договоре;
* использовать единый код для расчёта;
* изменять представление франшизы без изменения структуры договора;
* использовать разные представления франшизы для пользовательского интерфейса и печатных форм;
* однозначно определить применённое условие франшизы.

`deductibleCode` на уровне `InsuredObject` является значением по умолчанию для покрытий объекта.

Если конкретное покрытие имеет собственную франшизу, оно может переопределить общую франшизу своим `deductibleCode`.

```text id="w2y7ks"
Coverage.deductibleCode != null
        │
        ├── да → используется франшиза покрытия
        │
        └── нет → используется InsuredObject.deductibleCode
```

Если `InsuredObject.deductibleCode` также отсутствует, это означает, что общая франшиза для объекта не задана. Дальнейшее поведение определяется конфигурацией конкретного продукта.

### 12.14.5. Правило наследования франшизы

Франшиза может быть задана на двух уровнях:

```text id="q5v9pd"
InsuredObject
└── deductibleCode
        │
        ├── Coverage A
        │     └── deductibleCode отсутствует
        │           → используется общая франшиза
        │
        └── Coverage B
              └── deductibleCode = FIX1000
                    → используется франшиза покрытия
```

Таким образом, `InsuredObject.deductibleCode` задаёт общую франшизу по умолчанию, а `Coverage.deductibleCode` позволяет определить исключение для конкретного покрытия.

Например:

```json id="r1m6tz"
{
  "deductibleCode": "FIX300",
  "covers": [
    {
      "coverCode": "COVERAGE_A",
      "premium": 25000.00
    },
    {
      "coverCode": "COVERAGE_B",
      "deductibleCode": "FIX1000",
      "premium": 13450.00
    }
  ]
}
```

В данном случае:

* `COVERAGE_A` использует общую франшизу `FIX300`;
* `COVERAGE_B` использует собственную франшизу `FIX1000`.

При этом `deductibleCode` является ссылкой на конфигурацию, а не текстовым описанием франшизы.

### 12.14.6. Параметры покрытия

Каждый элемент `covers[]` содержит параметры конкретного покрытия:

```text id="n4c8yw"
Coverage
├── coverCode
├── option
├── sumInsured
├── risks[]
├── deductibleCode?
└── premium
```

Таким образом:

| Параметр         | Уровень         | Назначение                                    |
| ---------------- | --------------- | --------------------------------------------- |
| `packageCode`    | `InsuredObject` | Выбранный пакет/страховая программа           |
| `sumInsured`     | `InsuredObject` | Общая страховая сумма / лимит ответственности |
| `deductibleCode` | `InsuredObject` | Общая франшиза по умолчанию                   |
| `premiumTotal`   | `InsuredObject` | Сумма премий всех покрытий                    |
| `coverCode`      | `Coverage`      | Код покрытия                                  |
| `option`         | `Coverage`      | Выбранная опция покрытия                      |
| `sumInsured`     | `Coverage`      | Страховая сумма / лимит конкретного покрытия  |
| `risks`          | `Coverage`      | Массив кодов рисков                           |
| `deductibleCode` | `Coverage`      | Переопределение общей франшизы                |
| `premium`        | `Coverage`      | Премия конкретного покрытия                   |

### 12.14.7. Покрытия `InsuredObject`

`covers[]` содержит набор страховых покрытий, фактически применяемых к конкретному `InsuredObject`.

Покрытия определяются конфигурацией выбранного продукта и `packageCode`. В зависимости от выбранной программы покрытие может быть обязательным или опциональным.

В страховом контракте `covers[]` фиксирует выбранный и применённый набор покрытий вместе с параметрами, которые используются для расчёта и оформления договора.

```text id="z8k2rf"
InsuredObject
└── covers[]
    ├── coverCode
    ├── option
    ├── sumInsured
    ├── risks[]
    ├── deductibleCode?
    └── premium
```

| Атрибут          | Тип      | Описание                                                                     |
| ---------------- | -------- | ---------------------------------------------------------------------------- |
| `coverCode`      | string   | Код страхового покрытия                                                      |
| `option`         | string   | Код выбранной опции покрытия                                                 |
| `sumInsured`     | number   | Страховая сумма или лимит ответственности по покрытию                        |
| `risks`          | string[] | Массив кодов страховых рисков, входящих в покрытие                           |
| `deductibleCode` | string   | Код франшизы покрытия, если она отличается от общей франшизы `InsuredObject` |
| `premium`        | number   | Страховая премия по данному покрытию                                         |

#### `coverCode`

`coverCode` однозначно идентифицирует страховое покрытие в рамках конфигурации продукта.

Например:

```json id="c4p9vm"
{
  "coverCode": "CASCO_DAMAGE"
}
```

Код покрытия связывает данные страхового контракта с конфигурацией продукта, в которой определяются его наименование, доступность для выбранного `packageCode`, входящие риски, правила расчёта и другие параметры.

В самом контракте достаточно хранить `coverCode`. Полное описание покрытия не должно дублироваться в каждом договоре, однако фактически применённые финансовые параметры и условия должны быть сохранены в контракте.

#### `option`

`option` определяет выбранный вариант покрытия.

Опция используется в тех случаях, когда одно покрытие может иметь несколько вариантов исполнения, предусмотренных конфигурацией продукта.

Например:

```json id="y2f7qs"
{
  "coverCode": "CASCO_DAMAGE",
  "option": "FULL"
}
```

Допустимые значения `option` определяются конфигурацией продукта и должны интерпретироваться совместно с `coverCode` и версией продукта.

Если покрытие не имеет вариантов, `option` может отсутствовать.

#### `sumInsured`

`sumInsured` на уровне покрытия определяет страховую сумму или лимит ответственности, относящийся непосредственно к данному покрытию.

```json id="k7n3bx"
{
  "coverCode": "CASCO_DAMAGE",
  "sumInsured": 2000000
}
```

Значение может быть меньше общей страховой суммы `InsuredObject.sumInsured` или определяться независимо от неё в соответствии с правилами продукта.

Не для каждого покрытия `sumInsured` обязательно должен задаваться отдельно. Это определяется конфигурацией конкретного продукта.

#### `risks`

`risks` содержит коды страховых рисков, входящих в конкретное покрытие.

Это простой массив строк без дополнительной объектной обёртки:

```json id="m5r8tc"
{
  "coverCode": "CASCO_DAMAGE",
  "risks": [
    "ACCIDENT",
    "THEFT",
    "FIRE"
  ]
}
```

Каждый элемент массива является кодом риска, определённым в конфигурации продукта.

В контракте `risks[]` фиксирует фактически применённый набор рисков. Описание риска, его наименование и другие параметры определяются конфигурацией продукта по соответствующему коду.

#### `deductibleCode`

`deductibleCode` на уровне покрытия позволяет переопределить общую франшизу, заданную на уровне `InsuredObject`.

Если `Coverage.deductibleCode` отсутствует, используется:

```text id="s6q1wp"
InsuredObject.deductibleCode
```

Если `Coverage.deductibleCode` задан, применяется франшиза покрытия:

```text id="p4x9ka"
Coverage.deductibleCode
        ↓
приоритет над
        ↓
InsuredObject.deductibleCode
```

Например:

```json id="v6d2hs"
{
  "coverCode": "CASCO_DAMAGE",
  "deductibleCode": "FIX1000"
}
```

Таким образом, общая франшиза позволяет не дублировать одинаковое условие во всех покрытиях, а `Coverage.deductibleCode` позволяет определить исключение для конкретного покрытия.

#### `premium`

`premium` содержит страховую премию, рассчитанную для конкретного покрытия.

```json id="j3w7fn"
{
  "coverCode": "CASCO_DAMAGE",
  "premium": 25000.00
}
```

Премия является результатом расчёта с учётом параметров продукта, выбранного пакета, страховой суммы, рисков, опций, франшизы и других тарифных факторов.

Именно `Coverage.premium` является исходным значением для формирования общей премии объекта:

```text 
InsuredObject.premiumTotal =
    Σ covers[].premium
```

`premiumTotal` на уровне `InsuredObject` является агрегированным значением и не заменяет `premium` отдельных покрытий.

### Пример `covers[]`

```json id="t7q4mp"
{
  "covers": [
    {
      "coverCode": "CASCO_DAMAGE",
      "option": "FULL",
      "sumInsured": 2627469,
      "risks": [
        "ACCIDENT",
        "THEFT",
        "FIRE"
      ],
      "deductibleCode": "FIX1000",
      "premium": 25000.00
    },
    {
      "coverCode": "ASSISTANCE",
      "option": "STANDARD",
      "sumInsured": 500000,
      "risks": [
        "ROAD_ASSISTANCE"
      ],
      "premium": 13450.00
    }
  ]
}
```

В данном примере:

* `CASCO_DAMAGE` и `ASSISTANCE` — два применённых покрытия;
* каждое покрытие имеет собственный `coverCode`;
* `option` определяет выбранный вариант покрытия;
* `sumInsured` задаёт сумму или лимит конкретного покрытия;
* `risks[]` содержит коды рисков, входящих в покрытие;
* первое покрытие переопределяет общую франшизу объекта значением `FIX1000`;
* второе покрытие использует общую франшизу объекта, поскольку собственный `deductibleCode` не задан;
* `premium` содержит премию каждого покрытия;
* `premiumTotal` `InsuredObject` рассчитывается как сумма премий всех покрытий.

## 12.19. Drivers

`drivers` представляет список водителей, имеющих отношение к страхуемому транспортному средству.

```text
drivers[]
```

### Требуется определить атрибуты

Необходимо определить:

* состав данных водителя;
* обязательность водительского удостоверения;
* серию и номер удостоверения;
* дату выдачи;
* категории;
* стаж;
* дату рождения;
* ограничения по допуску к управлению.

## 12.20. Cargo

`cargo` представляет груз как объект страхования.

Груз может использоваться в страховании перевозки совместно с:

* перевозчиком;
* транспортом;
* маршрутом;
* пунктами отправления и назначения;
* перегрузочными пунктами.

### Требуется определить атрибуты

Полный набор атрибутов `cargo` в текущей концепции ещё не зафиксирован.

Необходимо определить:

* наименование груза;
* описание;
* количество;
* единицу измерения;
* вес;
* объём;
* стоимость;
* упаковку;
* характеристики опасности;
* температурный режим;
* другие параметры, необходимые для расчёта и андеррайтинга.

---

## 12.21. Carrier

`carrier` представляет перевозчика и является Party.

```text
carrier
└── Party
    ├── party
    ├── person? / organization?
    ├── documents[]
    ├── addresses[]
    ├── phones[]
    └── emails[]
```

Перевозчик является отдельной ролью Party и не должен смешиваться с самим транспортным средством.

---

## 12.22. Transport

`transport` представляет транспорт, используемый при перевозке.

Транспорт является массивом, поскольку одна перевозка может состоять из нескольких этапов и использовать разные виды транспорта.

Например:

```json
{
  "transport": [
    {
      "typeCode": "ROAD",
      "vehicle": {}
    },
    {
      "typeCode": "SEA",
      "vessel": {}
    },
    {
      "typeCode": "ROAD",
      "vehicle": {}
    }
  ]
}
```

Такая структура позволяет описывать мультимодальную перевозку и перегрузку между различными видами транспорта.

Тип транспорта определяется через `typeCode`.

---

## 12.23. Vessel

`vessel` представляет морское или речное судно, используемое как транспорт в перевозке.

В текущей концепции определены следующие характеристики:

| Поле           | Назначение         |
| -------------- | ------------------ |
| `name`         | Наименование судна |
| `imo`          | IMO                |
| `flagCountry`  | Страна флага       |
| `type`         | Тип судна          |
| `year`         | Год постройки      |
| `callSign`     | Позывной           |
| `registryPort` | Порт регистрации   |
| `tonnage`      | Тоннаж             |
| `deadweight`   | Дедвейт            |
| `owner`        | Собственник        |
| `operator`     | Оператор           |

Часть полей может потребовать уточнения типов и справочников.

---

## 12.24. Delivery

`delivery` описывает параметры доставки и перевозки.

`delivery` является отдельным объектом `insuredObject`, а не частью только `cargo`.

Причина такого решения заключается в том, что информация о доставке может быть необходима не только для страхования груза, но и для других страховых продуктов.

`delivery` может использоваться совместно с адресами застрахованного объекта, где адреса маршрута имеют типы:

```text
ORIGIN
TRANSSHIPMENT
DESTINATION
```

### Требуется определить атрибуты

Полный набор полей `delivery` ещё не согласован.

Необходимо определить:

* идентификатор перевозки;
* даты;
* маршрут;
* сроки доставки;
* условия доставки;
* дополнительные параметры перевозки.

---

## 12.25. Consumer Electronics

`consumerElectronics` является базовым специализированным объектом для страхования бытовой и потребительской электроники.

Он представляет предмет страхования, а не тип страхового покрытия.

Пример:

```json
{
  "insuredObject": {
    "consumerElectronics": {},
    "packageCode": "CE_BASIC",
    "sumInsured": 100000
  }
}
```

### Требуется определить атрибуты

Полный набор атрибутов `consumerElectronics` ещё не согласован.

Необходимо определить:

* тип устройства;
* производителя;
* модель;
* серийный номер;
* дату приобретения;
* стоимость;
* состояние;
* другие характеристики, необходимые для идентификации и расчёта.

---

## 12.26. Flight Segments

`flightSegments` представляет последовательность сегментов авиаперелёта.

Массив используется потому, что одна поездка может включать несколько перелётов.

```text
flightSegments[]
└── Flight Segment
```

Для сегмента определены следующие данные:

| Поле                | Назначение               |
| ------------------- | ------------------------ |
| `ticketPrice`       | Стоимость билета         |
| `currency`          | Валюта стоимости билета  |
| `departureAirport`  | Аэропорт отправления     |
| `arrivalAirport`    | Аэропорт прибытия        |
| `departureDateTime` | Дата и время отправления |
| `arrivalDateTime`   | Дата и время прибытия    |
| `airline`           | Авиакомпания             |

Пример структуры:

```json
{
  "flightSegments": [
    {
      "ticketPrice": 10000,
      "currency": "RUR",
      "departureAirport": {},
      "arrivalAirport": {},
      "departureDateTime": "2026-08-19T10:00:00+03:00",
      "arrivalDateTime": "2026-08-19T12:00:00+03:00",
      "airline": {}
    }
  ]
}
```

Набор атрибутов аэропорта и авиакомпании требует отдельного определения.

---

## 12.27. Специализированные атрибуты страхования

Помимо предметных объектов, `insuredObject` может содержать специализированные блоки параметров конкретного вида страхования.

Используется соглашение:

```text
<insuranceType>Attributes
```

Например:

```text
cascoAttributes
accidentAttributes
medicalAttributes
cargoAttributes
```

Эти блоки не являются универсальным контейнером для всех данных продукта.

Каждый блок содержит параметры, характерные именно для соответствующего вида страхования.

При этом не используется отдельный универсальный объект `programAttributes`.

---

## 12.28. Casco Attributes

`cascoAttributes` содержит специализированные параметры страхования транспортного средства по продуктам КАСКО.

В текущей модели определены:

| Поле                | Назначение                     |
| ------------------- | ------------------------------ |
| `coverageTerritory` | Территория страхового покрытия |
| `isAutostart`       | Признак наличия автозапуска    |
| `purpose`           | Назначение использования       |
| `usingType`         | Тип использования              |

Пример:

```json
{
  "cascoAttributes": {
    "coverageTerritory": "RU",
    "isAutostart": false,
    "purpose": "3",
    "usingType": "4"
  }
}
```

---

## 12.29. Accident Attributes

`accidentAttributes` предназначен для специализированных параметров страхования от несчастных случаев.

Полный набор атрибутов в текущей концепции не зафиксирован.

### Требуется определить атрибуты

Необходимо определить:

* параметры застрахованного лица;
* характеристики страхуемого риска;
* параметры программы;
* ограничения;
* другие данные, необходимые для расчёта продукта.

## 12.30. Medical Attributes

`medicalAttributes` предназначен для специализированных параметров медицинского страхования.

Полный набор атрибутов в текущей концепции не зафиксирован.

### Требуется определить атрибуты

Необходимо определить:

* территорию оказания помощи;
* программу обслуживания;
* категории медицинской помощи;
* сроки;
* ограничения;
* другие параметры продукта.

## 12.31. Cargo Attributes

`cargoAttributes` содержит параметры, специфичные для страхования груза.

Он дополняет объект `cargo`, но не заменяет его.

Таким образом:

```text
cargo
    ↓
что именно перевозится

cargoAttributes
    ↓
как этот объект страхуется
```

Полный набор атрибутов `cargoAttributes` ещё не согласован.

### Требуется определить атрибуты

Необходимо определить параметры, которые относятся именно к страхованию груза, а не к описанию самого груза или маршрута.

---

## 12.32. Типовые страховые продукты

Модель договора должна позволять описывать различные страховые продукты без создания отдельного формата контракта для каждого из них.

Типовой продукт определяется комбинацией:

```text
Product
├── Insured Objects
├── Product Attributes
├── Coverages
├── Risks
├── Limits
└── Calculation Rules
```

В рамках договора эта комбинация представляется через общие и специализированные части `insuredObject`.

---

## 12.33. Страхование автомобиля

Для страхования автомобиля основным объектом является `vehicle`.

Типовая структура:

```text
Insured Object
├── vehicle
├── vehicleDocument
├── vehicleOwner
├── drivers[]
├── packageCode
├── sumInsured
└── cascoAttributes
```

Типовые покрытия и риски определяются самим страховым продуктом и не являются частью базового объекта `vehicle`.

В дальнейшем для конкретного продукта необходимо определить перечень покрытий, рисков, франшиз, лимитов и условий их применения.

---

## 12.34. Страхование от несчастных случаев

Для страхования от несчастных случаев застрахованным объектом может выступать Party, представляющий физическое лицо.

Типовая структура:

```text
Insured Object
├── party
├── person
├── documents[]
├── addresses[]
├── phones[]
├── emails[]
└── accidentAttributes
```

Конкретный состав покрытий и рисков определяется продуктом.

---

## 12.35. Медицинское страхование

Медицинское страхование использует Party / Person как объект, связанный с застрахованным лицом.

Типовая структура:

```text
Insured Object
├── party
├── person
├── documents[]
├── addresses[]
├── phones[]
├── emails[]
└── medicalAttributes
```

Специализированные параметры программы медицинского страхования размещаются в `medicalAttributes`.

---

## 12.36. Страхование грузов

Страхование грузов использует несколько специализированных объектов одновременно:

```text
Insured Object
├── cargo
├── carrier
├── transport[]
├── delivery
├── addresses[]
└── cargoAttributes
```

Адреса могут представлять маршрут:

```text
ORIGIN
    ↓
TRANSSHIPMENT
    ↓
TRANSSHIPMENT
    ↓
DESTINATION
```

`transport[]` позволяет представить мультимодальную перевозку.

Например:

```text
ROAD → SEA → ROAD
```

При этом груз, перевозчик и транспорт являются разными предметными сущностями и не должны объединяться в один объект.

---

## 12.37. Авиастрахование

Для страхования пассажирской поездки используется Party / Person и набор сегментов перелёта.

Типовая структура:

```text
Insured Object
├── party
├── person
├── documents[]
├── flightSegments[]
└── ...
```

`flightSegments[]` позволяет описывать как прямой перелёт, так и поездку с пересадками.

Каждый сегмент содержит сведения о маршруте и времени перелёта.

---

## 12.38. Страхование потребительской электроники

Для страхования бытовой или потребительской электроники используется специализированный объект `consumerElectronics`.

Типовая структура:

```text
Insured Object
├── consumerElectronics
├── packageCode
└── sumInsured
```

Дополнительные параметры страхования могут быть представлены отдельным специализированным блоком, если они необходимы конкретному продукту.


---

## 12.40. Расширение модели

Одним из основных требований к модели является возможность добавления новых видов страхования без изменения базовой структуры контракта.

При появлении нового предметного объекта он добавляется как именованный объект `insuredObject`.

Например:

```json
{
  "insuredObject": {
    "property": {}
  }
}
```

При появлении нового специализированного типа страхования его параметры добавляются отдельным блоком:

```json
{
  "insuredObject": {
    "property": {},
    "propertyAttributes": {}
  }
}
```

Таким образом, расширение модели происходит за счёт добавления новых предметных объектов и специализированных атрибутов, а не за счёт создания отдельного формата договора для каждого продукта.

При этом новое расширение должно быть согласовано с Product Domain и правилами расчёта, поскольку сам факт наличия поля в JSON не определяет бизнес-смысл страхового продукта.

---

## 12.41. Snapshot и Master Data

Данные участников договора являются snapshot на момент создания или оформления договора.

`masterPartyId` позволяет сохранить связь с исходным объектом Master Data, однако эта связь не означает динамического наследования.

Например:

```text
Master Party
PARTY-010
     │
     │ copy
     ▼
Contract
CP-010
```

Если после оформления договора в Master Data изменяется адрес или контактный телефон:

```text
Master Party
PARTY-010
     │
     X  изменение не распространяется автоматически
     │
     ▼
Existing Contract
CP-010
```

Договор должен сохранять те данные, на основании которых он был рассчитан и оформлен.

Это особенно важно для юридически значимых документов и исторического воспроизведения состояния договора.

---

## 12.42. Quote и Policy

Одна и та же бизнес-модель контракта может использоваться как входная модель при предварительном расчёте и при оформлении договора.

Поэтому различие между Quote и Policy не обязательно означает наличие двух полностью разных входных JSON-моделей.

Если для расчёта и оформления требуется один и тот же набор исходных данных, может использоваться общий `InsuranceContractRequest`.

Различие между Quote и Policy в этом случае относится прежде всего к жизненному циклу и результату операции:

```text
InsuranceContractRequest
        │
        ├── Quote
        │     └── calculation result
        │
        └── Policy
              └── issued contract
```

---

Общая структура договора может выглядеть следующим образом:

```json
  "endDate": "2027-08-19T00:00:00+03:00",
  "issueDate": "2026-08-19T00:00:00+03:00",

    },
    "organization": {},
    "documents": [],

    "phones": [],
    "emails": []
  },

  "insuredObject": {
```

Этот пример показывает общий принцип композиции модели. Конкретный состав полей определяется страховым продуктом.

## 12.44. Правила моделирования

При добавлении новых объектов и продуктов следует придерживаться следующих правил:

1. Общие сущности должны быть переиспользуемыми.
2. Party, Person, Organization, Document, Address и Contact не должны дублироваться для каждого страхового продукта.
3. Предмет страхования должен моделироваться через `insuredObject`.
4. Специализированный предметный объект должен иметь собственное имя: `vehicle`, `cargo`, `vessel`, `consumerElectronics` и т.д.
5. Специализированные параметры страхования должны находиться в соответствующем `*Attributes`.
6. Универсальный `programAttributes` не используется.
7. `packageCode` и `sumInsured` являются непосредственными атрибутами `insuredObject`.
8. `transport` является массивом, чтобы поддерживать мультимодальные перевозки.
9. `delivery` является отдельным объектом `insuredObject` и не ограничивается страхованием груза.
10. `flightSegments` является массивом, поскольку поездка может включать несколько сегментов.
11. Party внутри договора является snapshot.
12. `masterPartyId` используется для указания происхождения данных, а не для динамического наследования.
13. Изменение Master Data не должно изменять уже существующий договор.
14. Новый страховой продукт должен собираться из существующих типовых объектов и необходимых специализированных расширений.
15. Если для нового объекта или продукта не определён набор атрибутов, он должен быть согласован до фиксации JSON Schema и API-контракта.


# 17. Документы и файловое хранилище

pt-files отвечает за файловый контур. В текущей технологии используются MinIO и PDFBox.

```text
Business document
       |
       v
Document metadata
       |
       +------> Object Storage (MinIO)
       |
       +------> PDF generation / processing (PDFBox)

```

Важно разделять документ как бизнес-сущность и файл как бинарный объект. Policy может иметь несколько документов, а один document record должен иметь понятный lifecycle и связь с бизнес-объектом.
Email-зависимости присутствуют в backend-контексте, однако точная схема notification service в текущем источнике не зафиксирована.

# 18. Номера и идентификаторы

pt-numbers отвечает за генерацию бизнес-номеров. В контексте зафиксирована поддержка placeholder-формата и reset policies, а для последовательностей упоминается pessimistic locking.

## Разные виды идентификаторов


Идентификатор | Назначение

|---|---|

|Technical ID|Внутренний уникальный идентификатор сущности|

|Business number|Номер полиса/документа, видимый бизнесу|

|partyId|Идентификатор Party snapshot|

|masterPartyId|Источник Party в Master Data|

|productCode|Код продукта|

Business number и technical ID не должны смешиваться. Номер полиса может иметь бизнес-правила генерации и форматирование, тогда как technical ID должен оставаться стабильным техническим ключом.

# 19. Платежи и комиссии

Модуль pt-payments существует в текущем backend. Однако конкретный payment provider и полный lifecycle в предоставленном контексте не зафиксированы.

```text
Policy / Invoice
      |
      v
Payment Created
      |
      v
Provider / payment channel
      |
      v
Result
      |
      +--> success
      +--> failure
      +--> refund

```

Для финансовых операций рекомендуется обеспечивать идемпотентность, correlation ID и явное хранение provider reference. Эти пункты относятся к архитектурным требованиям, если соответствующий финансовый workflow будет реализован.
Комиссии также присутствуют как доменная область, но точная схема settlement не подтверждена текущим контекстом.

# 20. Claims и незавершённые области

В контексте присутствует privilege для claims, однако отдельного pt-claims модуля нет. Следовательно, claims следует считать частично определённой/незавершённой областью, а не готовым самостоятельным bounded context.
Шаблон CONTEXT.md содержит типовой FNOL/Claims lifecycle, но он не является доказательством реализации в текущем репозитории.

## Event-driven architecture

В pt-process обнаружена зависимость jakarta.jms-api, а ActiveMQ starter присутствует в закомментированном виде. Это указывает на возможный процессный/event-driven контур, но не подтверждает работающий message broker в production.

# 21. API и интеграционные границы

REST API является основным внешним контрактом backend; Springdoc OpenAPI используется для описания API.

## Ключевой принцип

API DTO не должны быть зеркалом database entities. Они описывают внешний бизнес-контракт.

## Quote / Policy

Если входные поля одинаковы, допустимо использовать общий InsuranceContractRequest. Разные response/resource модели при этом остаются нормальными.

## Идемпотентность

Для критических операций, особенно выпуска полиса и финансовых действий, необходимо иметь явную стратегию идемпотентности. Конкретный реализованный механизм следует подтверждать endpoint-кодом.

# 22. Данные, миграции и Source of Truth

PostgreSQL является центральным persistent storage. JPA используется для persistence, а миграции в текущем контексте выполняются Flyway.

## Source of truth hierarchy


Уровень | Вес

|---|---|

|Текущий исходный код|Максимальный|

|DB migrations|Очень высокий|

|Runtime/config|Высокий|

|Tests|Высокий|

|API contracts|Высокий|

|Текущая документация|Средний|

|Исторический README / vision|Низкий|

Если документация расходится с кодом, документ должен быть исправлен или явно помечен как proposed. Нельзя незаметно подменять реализованную архитектуру желаемой.

## Data model vs business model

Business JSON contract документируется отдельно от JPA/DB схемы. Это позволяет менять storage без изменения внешнего API.

Spring Boot Actuator присутствует в backend и предоставляет health endpoint. Полный production stack логирования, tracing, metrics backend и alerting в текущем контексте не определён.

## Минимальный эксплуатационный контур

- Health/readiness проверки.

- Structured application logs.

- Correlation ID для межмодульных операций.

- Метрики API и расчёта.

- Ошибки выпуска полиса и платежей.

- Контроль времени ответа Calculator/Rules.

# 25. Архитектурные принципы

- <b>Business model first.</b> Сначала фиксируется смысл сущности, затем DTO и persistence.

- <b>Immutable product versions.</b> Published Product Version не меняется задним числом.

- <b>Policy snapshot.</b> Полис сохраняет данные, использованные при оформлении.

- <b>Master Data is provenance.</b> masterPartyId — источник, а не runtime inheritance.

- <b>Tenant isolation server-side.</b> Нельзя полагаться только на tenantId из URL.

- <b>Privilege + scope.</b> Permission и область данных — разные измерения доступа.

- <b>Extensible InsuredObject.</b> Новые страховые типы добавляют специализированный *Attributes блок.

- <b>No generic programAttributes.</b> Специализация должна быть явно именована.

- <b>Transport is a list.</b> Мультимодальная перевозка требует массива transport[].

- <b>Documents are not identifiers.</b> INN/KPP/OGRN/SNILS — реквизиты, а не документы.

- <b>Modular monolith first.</b> Модули разделяют ответственность без преждевременного перехода к микросервисам.
